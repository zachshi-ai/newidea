# 你的周报在说谎 —— 从 git 历史打捞不可见工作

首先，感谢大家在百忙之中参加今天的分享，也感谢组委会的信任和安排，让我有机会站在这个讲台上。废话不多说，接下来我将用接下来的十几分钟，和大家聊一个我观察了很多年、也困扰了很多年的现象。在正式开始之前，也感谢我所在团队的小伙伴们，这个题目里的一半素材来自他们。

## 一个熟悉的场景

请大家回想一下上周五下午。你打开周报文档，光标闪烁，脑子里一片空白。你明明忙了一整周——救火、review 代码、帮新人搭环境、排查一个诡异的线上问题——但文档里能写的，好像只有两行。你开始怀疑自己：这一周到底干了什么？

与此同时，你的同事写了满满一页：完成了某某项目三期需求，推进了跨部门对齐，输出了技术方案。领导扫一眼，一个「产出可疑」，一个「输出饱满」。但你心里清楚：他那一页里有一半是计划中的事，而你救的那把火，烧掉了整整两天。

这两个人的差距，不是努力程度的差距，是**工作被看见的能力**的差距。而我们整个绩效体系，恰恰只奖励后者。长此以往，组织里会留下两种人：擅长把工作讲成故事的人，和慢慢学会把故事讲成工作的人。真正安静做事的第三种人，正在流失。

## 周报制度的前世今生

要理解这个问题，我们得先回到周报制度本身。周报的历史沿革可以追溯到上个世纪的管理实践。很久以前，工厂主管就需要每周向厂长汇报产量；在过去的管理学教材里，定期书面汇报被视为控制论的直接应用：管理者无法观察所有过程，于是要求过程被「书写」出来。传统上，这套做法沿用了几十年，从纸面搬到邮件，再从邮件搬到协作平台，形式变了三茬，内核一字未改：由员工手工申报工作。

而手工申报有一条铁律：**可申报的工作，才被看见**。这条铁律在制造业没什么问题——拧了多少颗螺丝，数得清，报得出。但软件开发不是拧螺丝。工程师的很大一部分工作，恰恰是「消解问题」而不是「交付东西」：把一个未来的事故提前拆掉、把别人的阻塞疏通、把混乱的代码理顺。这些工作完成得越好，痕迹越少。做得越好，越像什么都没做。

更麻烦的是，我们没有任何一个人能看到全貌。领导看不到你周五凌晨的告警群，你自己也记不清三周前修的那个依赖冲突。信息不是被谁藏起来了，是被时间冲散了。

## 两种失败反应

面对这条裂缝，组织尝试过两种反应，都很自然，也都失败了。

第一种反应是把表格做细：逐项工时、项目编号、进度百分比，仿佛只要格子够多，真相就会自己填进来。结果恰恰相反——表格越细，填写的心智成本越高，员工就越倾向于「先做容易填进格子的工作」。度量塑造行为，格式塑造度量。半年之后，表格填得整整齐齐，看不见的工作依然看不见，看得见的工作开始注水。

第二种反应更激进：干脆取消周报。过去几年不止一家大厂宣布「去汇报化」，砍掉各种定期文档。员工当然欢呼，但问题并没有消失，只是被推迟了——推迟到季度汇报、晋升答辩、绩效校准的那个下午，你还是要凭记忆证明自己做过什么。取消了排练，没有取消考试。信息源还是那条不可靠的记忆。

两种反应失败的根源是同一个：都在调整「申报的格式和频率」，没有动「申报的信息源」。而信息源的问题，前面已经说过了——记忆是偏振镜头，只放行特定方向的光。

## 三个真实的下午

我讲三个下午，都是真事，细节做了脱敏。

第一个下午，一位高级工程师花了 4 个小时，帮一个新项目排查为什么构建在 CI 上随机失败。最后定位是缓存键冲突，改动只有 2 行。这 2 行进入了他名下的提交记录，但这 4 个小时的排查过程，没有任何地方记得。

第二个下午，一位架构师做了 6 轮代码评审，横跨 3 个项目，提出了 40 多条意见，其中 11 条是会引发线上问题的缺陷。这些意见救了 3 次事故——但评审者名下的 commit 数量是零。周报里写什么？写「参加评审若干」？

第三个下午最讽刺。一位同学花了一整个下午写周报——美化措辞、调整结构、把琐碎的工作包装成「专项治理」。这可能是他一周里唯一一件投入产出比最高的事，因为周报是唯一会被读到的东西。工具主义者赢了，系统输了。

## 数字会说谎

个例说完，我给大家一组数字。在 2024 年我们对 1 个 200 人研发团队做的统计里，每周人均提交 17 个 commit，但周报里提到的平均只有 5 个，覆盖率 29%。更扎眼的是另外两个数：一个季度里被修复的 bug 有 312 个，其中 207 个的修复工作从未出现在任何周报里，占 66%；而周报里出现的「计划推进类」条目，有 58% 在 git 历史里找不到对应动作。

也就是说：三分之二的返工劳动在管理体系里不存在，而一半以上的申报内容在代码库里不存在。两边各说各的谎。

> 你无法管理你不能衡量的东西——但你衡量的，正在悄悄变成你唯一会做的东西。

那真实的工作去哪了？它们都在，只是换了一本账。git 历史就是那本账。看不见的工作，大体可以列成三类：

- 救火与线上排查：从告警到根因，全程不产生一个「交付物」
- 代码评审：一小时的 review 换来别人代码的质量，自己名下零提交
- 隐性维护：升级依赖、修构建、补文档，每一件都小到不值得写，大到不能不做

而这三类工作在 git 里都有确凿的痕迹。排查有 commit 和回滚记录，评审有 review 评论，维护有琐碎但连续的提交链。比如你要打捞自己上一周的真实全貌，只需要一句：

```bash
git log --since="last week" --author="$(git config user.name)" \
  --no-merges --stat --format="%h %ad %s" --date=local
```

举个例子，具体来说，上上周我帮隔壁组排查了一次数据库连接池泄漏，花了整整 6 个小时。这件事在我的周报里不存在，因为它不是我的 KPI，我甚至不确定该写进哪一栏。但在 git 历史里，它留下了 4 个 commit、23 个文件的改动和 2 个被回滚的错误假设。工作可以不被讲述，但很难不留痕迹。

这里要多说一句什么叫「确定性重建」：同样的命令，任何人、任何时候、在任何一台机器上跑，得到同一份结果。它不完美——你的灵感、你的沟通、你在白板前的争论都不在 git 里，所以它给出的是工作量的**下界**，不是全貌。但一份人人可复算的下界，好过一份人人不可复算的上界。前者可以讨论、可以修正、可以积累；后者只能选择相信或者不信。

那打捞出来的全貌长什么样？我们组用这套方法跑了一个季度。每周五下午四点，工具自动生成事实段：本周 14 个提交、横跨 3 个项目，其中 5 个是修复、2 个是重构、4 个评审意见被采纳；附一条趋势——你的评审占比连续三周上升，说明团队对你判断力的信任在上升，这在任何手工周报里都不会被写成「产出」。最意外的是撰写时间：过去一份周报平均要磨 40 分钟，现在补两段语境 10 分钟收工。省下的不只是时间，是那种周五傍晚「自证清白」的疲惫感。

## 真正的问题

讲到这里，我认为真正的问题不是员工懒于写周报，也不是领导只看表面数字——而是我们让**最不了解全貌的人，凭记忆手工申报全貌**，然后把申报结果当成管理依据。

记忆是有偏的，而且是系统性偏差：它偏爱完整的、有名字的、能讲成故事的工作；它天然丢失碎片化的、防御性的、消灭问题的工作。心理学里这叫峰终定律和叙事偏差的合谋：你会记住发布会，忘记深夜告警；记住大项目，忘记小疏通。这不是态度问题，是认知结构问题。靠「提醒大家认真写周报」解决不了，就像靠「提醒自己记得梦境」解决不了遗忘。

所以我的主张是：把周报从「申报制」改成「对账制」。工具先从 git 历史里确定性重建你这一周的真实工作全貌——哪些提交、哪些评审、哪些修复、哪些重构——先摆给你看，你再来补充语境和判断。员工不再凭记忆自证清白，领导不再靠文采给工作量打分。

注意，对账制不是监控。恰恰相反：它把「事实」固定下来，反而保护了员工——你不需要担心自己「看起来不够忙」，因为你的忙是有据可查的；你也不需要担心被监控，因为对账暴露的是工作痕迹，不是工作时长。这是和打卡类工具的本质区别。

对账制的周报长什么样？三段式：

- 事实段：由工具从 git 历史生成，一行人也不能改，人人可复算
- 语境段：员工补充「为什么做这些」，这是记忆真正可靠的部分
- 判断段：下周的风险与依赖，留给人类发挥判断力的部分

推行的时候要守住三条底线：只统计、不排名；只对账、不评优；数据本人可见先于上级可见。让工具先赢得写周报的人，再赢得读周报的人。

## 三个常见反驳

讲到这里，通常会有三个反驳，我试着正面回应。

第一种反驳说，周报的本意是对齐信息，不是度量产出，你把它做成了考勤。我的回答是：正因为对齐需要的是真实信息，才更应该从事实段开始对齐。现在的周报对齐的是什么？是双方各自记忆和措辞的妥协产物。事实段摆出来之后，讨论才能从「你上周做了什么」这种自证题，前进到「这周的风险怎么拆」这种真问题。对账不是加强了对产出的审计，是降低了对齐的噪音。

第二种反驳说，这就是监控，换了个好听的名字。我的回答是看三条底线：只统计、不排名，杜绝内卷式比较；只对账、不评优，杜绝拿工具当绩效；本人可见先于上级可见，杜绝暗箱。监控的本质是单向的不透明，对账的本质是双向的可复算——你的领导同样没法再凭印象描述你的工作了，这对安静做事的人是保护，不是威胁。

第三种反驳说，我不是写代码的岗位，git 对我没用。这个反驳是对的，但不致命。对账的原则从来不绑定 git：设计师的账本是设计稿的版本历史，运营的账本是工单和投放记录，产品的账本是需求文档的变更历史。原则只有一条——**先用可复算的事实打底，再用人的叙事补充**。账本各不相同，原则处处适用。

如果把三种反驳放在一起看，会发现一个有趣的共同点：它们都在担心「事实被用错」，而不是「事实不成立」。这其实是对账制最好的广告——连反对者都不否认 git 历史比记忆可靠，他们担心的从来是第二步：这些事实交到谁手里、按什么规则使用。所以真正要设计的不是打捞工具，打捞只是前提；要设计的是使用规则，也就是前面那三条底线。规则立住了，工具才敢交出去。

## 结尾

今天想讲的其实只有一件事：当度量体系只奖励「留下名字的工作」，组织就会系统性地惩罚「消解问题的人」。而这些人，恰恰是你最不能失去的人——他们安静，是因为他们把噪音都消灭在了你看不见的地方。

改掉度量，比劝他们「学会表现自己」便宜得多，也体面得多。

如果明天想试一件小事：不用推什么制度，就打开终端，跑一遍上面那条命令，看看自己上一周的真实全貌。你会重新认识那个周五下午词穷的人——他不是没干活，他只是没法凭记忆证明。给他一本账，他会写得比你想象的好得多。

谢谢大家。
