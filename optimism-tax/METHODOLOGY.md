# METHODOLOGY · 乐观税定价学

> optimism-tax 的税率不是修辞，是一本从收据确定性重建的账。本文记录每一条记账规则的动机、边界与已知局限。

## 1. 立场：审计承诺，不考核人

规划谬误（planning fallacy）是行为经济学里被复制了四十多年的发现：人预测自己的任务耗时系统性偏短，且**即使经历过无数次低估也不校准**——Kahneman 与 Tversky 的原始实验里，学生预估毕业论文用时 34 天，实际中位 55.5 天，而问他们「最坏要多久」时说的数字都不够实际均值。更关键的观察是：**让预测失效的从来不是知识，是视角**——问「别人做这类事要多久」估得比「我做要多久」准得多（inside view vs outside view）。

由此推出本工具最重要的立场分离：**税率不是绩效分**。税率服务的对象是「听你报价排期的人」——他要的是你的数字的真实含义，不是你的能力评价。一个税率 3.5x 的研究员可能恰恰是团队里最敢接未知问题的人：他的失真是任务性质（不可调研就不能立项的探索）的镜像，不是懈怠的证据。本工具只回答「你的 X 天统计上是几天」，永远不回答「你是不是在摸鱼」——后者是绩效面谈的辖区，不是定价学的辖区。

## 2. 为什么是中位数，不是平均数

膨胀比 r = actual ÷ estimate 是一个右偏分布：下界被 0 锁死（最多「没花时间」），上界没有锁（调研可以爆 10 倍）。在右偏分布上，平均数被尾部绑架——一次 20x 的灾难能把九次 1.5x 的诚实劳动拉成 3.35x 的「重税」。中位数回答的才是排期会上那个问题：**典型的一次任务，超出估算多少倍？**

但中位数只进税率（描述典型），不进报价（承诺尾部）：P80 报价用的就是分位数，灾难的尾巴被如实抬进安全报价。两个数字各司其职——**税率告诉你你是谁，P80 告诉你该承诺什么**。九次 1.5x 加一次 20x：税率 1.5x（你不是传说中大坑），P80 却显著抬高（那次灾难属于你承诺分布的一部分）。

## 3. 为什么报价用 P80：reference class forecasting 的个人化

Kahneman 方法学里对 planning fallacy 的经典处方是 **reference class forecasting**：别问「这个任务要多久」（inside view），问「和我同类的历史任务实际花了多久」再取分布的高分位。配套工具（如参考类别预测程序）通常取第 80 分位——因为承诺要付违约代价，五次里晚一次是大多数协作关系能承受的频率；取 P50 就是五次里晚三次，取 P95 则报价虚高到没人信。

本工具把这件事做到极致：参考类别就是你自己的历史，连「别人的数据不适用于你」的最后一层质疑也消掉了。`quote 3` 给两行价——P50（你意思上的价格）与 P80（你该承诺的价格）——**价差本身就是失真的可视化**：校准好的人两行几乎重合，重税的人两行差出一倍。

## 4. 样本门槛：为什么是 8 条才报价，3 条才给桶税率

- **8 条报价门槛**：中位数是小样本下相对稳健的统计量，但「相对」不等于「无懈可击」。8 条以下的账本里，一条异常收据就能把税率搬走 20%+——此时报价等于**把工具的权威借给掷硬币**。拒绝报价不是功能缺失，是立场：宁可说「我还不知道你」，也不编一个数。门槛同时写进红旗（`TOO FEW RECORDS`），让账本自己解释自己为什么拒单。
- **3 条桶税率门槛**：`report` 的分桶账本展示每个 tag 的税率，但 <3 条的桶只标 `thin` 不给数字——两条收据算出的「税率」毫无意义，却会在报告里和真实税率长得一模一样。quote 层面的 tag 校准门槛更高（仍要 8 条），不够就回退全局并**声明依据**——回退必须可见，否则「用 research 校准」和「用全体校准」在输出上无法区分，报价就成了一件标错价签的衣服。

## 5. 两种失真都要治：藏 buffer（sandbagging）

膨胀比 <1 的收据不全是好事。提前完成有两种成因：真的校准好（P50 报价者），以及**报高数藏安全余量**——frank 的 ops 类 0.71x 不是美德，是另一种失真：他的报价虚高，团队按他的高报价排期，后段资源在空转；更糟的是 sandbagging 会污染「提前完成 = 校准好」的直觉，让虚报者长期免税。所以账本里提前完成的**比例**（>40% 且样本足够）触发 `SANDBAGGING SUSPECTED` 红旗——注意它只对「整体提前比例异常」报警，不指控单条提前收据：偶尔提前是运气，次次提前是定价策略。

## 6. 边界情形的处置

| 情形 | 处置 | 理由 |
|---|---|---|
| 半截收据（有 estimate 没 actual） | 跳过并计数，报告头显示 skipped | 账本污染不可逆污染统计，但「有一条没收完」本身就是信息，静默吞掉等于伪造整洁 |
| estimate ≤ 0、actual < 0、bool 伪装数字 | 拒收（record 直接失败，load 跳过计数） | 负估算在语义上不是「乐观」，是坏数据；bool 是 int 子类，必须显式挡在门外 |
| 完全未知的 tag（typo：`resarch`） | quote 拒绝（exit 3） | 静默回退全局会用全体税率给一个错误标签报价——**校准必须可追溯** |
| r 极端（一次 20x 灾难） | 不剔除 | 灾难是历史的一部分：税率（中位数）免疫它，P80（报价）包含它，各得其所 |
| 任务跨多天 / 被打断多次 | 不建模 | 收据只认 (estimate, actual) 对，打断的贡献已经含在 actual 里——内部归因是工时系统的事 |
| 多人共用一本账 | 直接可用（tag 区分不了人，加 `--file` 人各一本） | 桶税率按任务类型分不按人分，是因为「同一个人的不同类任务」失真差异远大于「不同人同类任务」——见样例账本 |
| 团队想强制报 P80 | `report --fail-under` 只管税率不管报价 | 门禁工具不越权到报价语义；强制流程是排期会主持人的职责 |

## 7. 已知局限（v1 不做，及为什么）

- **不自动接入 Jira / Linear**：估时审计的价值恰恰在「从你自己嘴里说出、你自己手上结束」的闭环；接工具 API 会引入「估算被中途修改」的污染（Jira 的估时是可变字段），收据必须是**不可变的历史事实**。
- **不做置信区间 / 显著性检验**：账本面对的是一个不断漂移的非平稳过程（人会被经验改变），「上周和这周差异 p<0.05」这类问题在 8-50 条的量级下问不出来；趋势的 worsening/improving 判定用了 1.5x/0.67x 的效应量阈值而不是 p 值，明确回答的是「变化大到值得注意吗」，不是「变化显著吗」。
- **不跨人比较排名**：一旦税率变成排行榜，sandbagging 就从个人策略升级为制度行为——账本只跟自己的过去比（趋势），不跟同事比。

## 8. FAQ

**Q：这和 story point 什么关系？**
A：不冲突，对象不同。story point 度量**相对复杂度**（这个比那个大几倍），本工具度量**换算率的失真**（你的 1 个点在日历上到底是几天）。团队 Velocity 就是集体的点→天换算率——乐观税是它的个人化 + 分类型版：Velocity 说「团队每周 20 个点」，乐观税说「你的 research 类点，1 个顶 3.5 个」。

**Q：既然估不准，直接用 P80 报价不就行了，为什么还要记账？**
A：P80 从哪来？没有账本的团队只能全体乘一个拍脑袋系数（业界常见的「乘 2 再加一天」），它对所有人都一样——而失真是分类型、分个人的。样例账本里全局系数 1.25 对 feature 类刚好、对 research 类差三倍：**没有分账的系数是新的玄学**。

**Q：故意低报（想让自己显得快）的人怎么办？**
A：账本治不了动机，治得了后果——他的 r 会持续 <1，`SANDBAGGING` 红旗亮出「40%+ 提前完成」的证据；而 P80 报价逻辑同样适用于反向校准：提前完成比例高的人，其 P80 会低于 P50 的合理邻域，报价系统如实呈现这个倒挂。

**Q：单位必须是天吗？**
A：收据不解释单位，只要求 estimate 与 actual 同单位。用小时、故事点、人日皆可——膨胀比是无量纲的。唯一建议：**一本账一种单位**，混单位的账本算出的税率没有含义。
