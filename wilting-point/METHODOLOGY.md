# 凋萎点 · METHODOLOGY

本文回答四件事：模型为什么长这样、刻度从哪来、哪些东西被故意简化了、以及常见问题的边界在哪里。

## 1. 立场：植物死亡是可预测的倒计时，不是突发事件

你「发现」叶子蔫了的那天，永远晚于植物「注定」的那天。土壤从湿到干的进程是单调的：上次浇水之后，每盆植物距离它的安全线（开始受损）和凋萎线（不可逆损伤）各有一个确定的天数——只要两本账（台账 + 浇水日志）是准的，水位计就是准的。工具的全部工作是把这两条线写在明处，然后把**你的行为**（浇水间隔的历史分布）摆到线的旁边对账。

## 2. 模型：单桶水位计，四档判定

### 2.1 为什么是它

每盆植物被建模为一个桶：浇水时充满，之后按天蒸发。模型只需要两个参数——**安全线 `dry_min`**（多久不浇开始出问题）和**凋萎线 `dry_max`**（多久不浇不可逆）。判定是两行比较：

```
d = 今天 − 上次浇水
d ≥ dry_max            → WILTED      （越过凋萎点）
d ≥ dry_min            → PARCHED     （伤害区间）
d ≥ 0.7 × dry_min      → DUE         （浇水窗口已开）
其他                    → OK
```

0.7 这一个系数把「该浇了」从一个时刻展开成一个**窗口**：窗口打开不等于死亡逼近，它给「今天 vs 周末」留了余地；真正要紧的是后两档。

### 2.2 它忽略了什么（以及为什么可以）

真实蒸腾取决于光、温、湿、盆材、土质、植株大小——全都没建模。替代方案是土壤湿度传感器，但那把门槛从「记一笔账」抬高到「买一堆设备」，而且传感器同样需要 `dry_min/dry_max` 的品种先验才能报警。本件选择把误差**显式化**：两根线写在台账里逐盆可调，你比任何模型都清楚你家那盆蕨住在干燥的南窗还是潮湿的浴室。确定性账本 + 可校准的线，好过一个无法审计的黑盒模型。

## 3. 刻度的来历

### 3.1 内置品种表

`species` 命令的 16 种（安全线/凋萎线）是常见室内园艺共识区间的**粗略中位**（如虎皮兰 21/45、绿萝 7/15、波士顿蕨 4/8），按「可忘记天数」而非「建议浇水频率」标定——建议频率说的是「最好几天一浇」，本件要的是「几天不浇会出事」，后者才是倒计时的刻度。台账里直接写数字，不引用表：表是参考，账本是事实。

### 3.2 季节系数

`--season summer` 把两根线 ×0.7（蒸腾快，可拖延时间缩短 30%），`--season winter` ×1.3。系数粗、方向对：夏天「怎么突然就要浇了」第一次有了刻度上的解释。同一本账，夏冬各跑一次，差异自己看。

### 3.3 半线与烂根灯

OVERWATER 的判定：**最近两次**浇水间隔都 **严格小于** 安全线 ÷ 2。三个设计点：

- **连续两次**：单次手滑是噪音，连续两次才是习惯——它抓的是「养护模式」，不是事故；
- **半线而非全线**：全线之内的浇水在名义上「没错」，但持续把耐旱植物泡在半线以下正是烂根的定义——这盏灯报警的对象是「在错误的时间做正确的事」；
- **严格小于**：恰好等于半线不亮，边界从宽，减少误报。

## 4. 主人画像：中位数，以及对它的三种用法

你的**中位浇水间隔** = 全部盆、全部历史间隔合并后的中位数。选中位数不选均值，理由与仓库同源（乐观税、续命账）：间隔分布右偏（一次出差就是一个 15 天的离群值），中位数是「你的正常节奏」的稳健估计。它被用在三处：

1. **失配率**：安全线严格小于你中位间隔的盆数占比——这些盆「要求你变成另一个人」；
2. **黑名单**：任一间隔严格大于该盆安全线记 1 次失调，按品种聚合 ≥2 次入榜——判据是行为，不是结果（枯死了才算就太晚了）；
3. **购入门卫**：安全线 s 对中位 m 的三档——s ≥ 1.5m（COMPATIBLE）、m ≤ s < 1.5m（RISKY）、s < m（INCOMPATIBLE，exit 4）。1.5 的 margin 的含义：容忍你迟到半个周期还有余量。

「恰好在安全线上」不算失调、恰好等于半线不亮灯、恰好等于中位不算失配——三处边界全部**严格**取向，统一从宽：工具的职责是对账，不是定罪。

## 5. 出差推演：两个场景，而不是一个提醒

`simulate trip N` 同时跑两个世界：

- **不浇走**：谁的凋萎日（上次浇水 + dry_max）落在 (今天, 回程日] 内——现状的世界；
- **浇完走**：假设离开当天统一补浇，时钟全部归零，凋萎线 ≤ N 的依然会沉——行动后的世界。

两个世界的差集就是托付清单。命名上它叫 `simulate` 而不是 `remind`，因为它是**反事实对跑**：先看不动手会怎样，再看最廉价的动手（离开前浇一遍，10 分钟）能救回多少——结论往往是「托付一盆」，而任何提醒类工具都只会说「记得安排人浇水」。

## 6. 边界情形

- **never-watered**：买回后日志里一行都没有的盆，`last_watered` 回退到 `acquired`（苗圃的那次算最后一次），并在报告里亮 NEVER-WATERED 牌——「买回来就忘了」也是一种死法，账本不装作没看见；
- **as_of**：默认取台账 `acquired` 与日志日期的最大值（时钟是账本的一部分，不是墙上的钟）；`--today` 拨表到任何日志日期之前是输入错误（exit 3）——过去的水位有意义，未来的水位没有；
- **浇水早于购入 / 同盆同日重复 / 未知植物**：一律带行号拒绝（exit 3）。账本的干净是所有读数的前提；
- **空日志**（刚开账）：水位计照常工作（回退到购入日），画像/黑名单/advice 显示 n/a——advice 会说「先养一个月再来问」：没有行为数据，判决免谈；
- **盆数 1 也成立**：模型没有对盆数的假设，一盆蕨和多肉混住的窗台同样适用。

## 7. 记录规范

- 一次**充分**浇水记一行（浇透），蜻蜓点水的润湿不算——模型假设每次浇水都充满桶；
- 换盆、施肥不记（它们不重置水位）；出差前代浇记一行并备注（账本不区分谁浇的，只关心桶满没满）；
- `dry_min/dry_max` 按盆校准：同一株蕨搬到浴室，两根线都可以放宽——线是「这盆」的，不只是「这个种」的；
- 日志支持第三列备注，进账不进算——它存在的意义是让 2026-08-18 那行「再也没浇过」在一年后还读得懂。

## 8. FAQ

**Q：为什么不直接用土壤湿度传感器？**
A：可以，两者不冲突。传感器解决「现在多湿」，本件解决「你的行为与它的需求差多远」——失配率、黑名单、购入判决、出差推演都不需要传感器，需要的是你三个月的浇水日志。传感器是从设备读数的账本自动化，随时可以接进来。

**Q：浇多少水重要吗？**
A：本件只记事件不记剂量，这是有意的简化：剂量数据手编成本高、误差大，而「间隔模式」已经足以解释绝大多数室内植物死亡（干旱轴 + 烂根轴）。真要抠剂量，备注列是自由的。

**Q：我的多肉明明每周浇一次也没死？**
A：可能。半线是**风险**刻度不是死刑判决——光照强、土质疏水好的多肉可以承受更密的浇水。但统计上「每周浇一次的多肉」是烂根高发人群，灯亮的意思是「你的习惯在这个盆上押了高赔率的注」，不是「它明天必死」。

**Q：黑名单会不会太武断？**
A：它只回答「这个品种在你的历史行为下反复越线」。搬到浴室、换疏水土、装自动浇水，任何一条都构成推翻它的理由——但那需要你**改变某个条件**，而改变的前提是先看见名单。

**Q：为什么 verdict 的措辞是「a lesson, not a guilt trip」？**
A：因为越过凋萎线的盆已经救不回来了，此刻的愧疚没有标的。工具把你的注意力推向还有救的：PARCHED 的今天浇，DUE 的排进日程，WILTED 的进黑名单复盘。账本记账，不记仇。

## 9. 已知局限（v1）

- 品种表的刻度是粗略中位，同种内差异（品种、株龄、盆土）可能到 ±50%——表是起点，校准是常态；
- 蒸腾不随天气建模（连续阴雨与连续晴天的消耗不同），季节系数是最粗的一阶修正；
- 浇水剂量不建模（见 FAQ）；
- 出差推演假设离开当天能一次浇透所有盆——做不到的话，把那天当成两次 `trip` 的起点手动分段；
- 没有提醒推送——本件是账本不是保姆，设计上它假设你会在浇水前、买花前、订机票前各跑一次。
