# 深夜灯火 · Methodology

> 本文回答三件事：为什么 git 时间戳能当过劳证据（以及它何时撒谎）、阈值是怎么定的、以及最重要的——这个工具的伦理边界在哪里。

---

## 1. 为什么时间戳比问卷诚实

过劳检测的传统手段是自报数据：问卷、1:1、敬业度调查。它们共同的问题是**社会期许偏差**——在考核关系里，没人会对经理说「我连续三周没休息了」，因为这听起来像抱怨或能力不足。

提交时间戳是另一类数据：**观察数据**。它不是为了回答「你累不累」而生的，只是诚实地记录了「代码在几点被写下」。它不受表演影响，不受回忆美化影响，且可回溯——你能看见燃烧是从哪一周开始的。

但这不等于「时间戳 = 工时」。它是**有偏样本**（只记录到提交时刻的工作），偏差方向是：低估总量（本地工作不提交）、但方向正确（深夜提交意味着深夜工作存在）。作为**趋势信号**足够，作为**工时对账单**不合格——本工具只做前者。

## 2. 时区：一个被大多数脚本做错的事实

git 的 author date 存储格式是「本地钟点 + UTC 偏移」，如 `2026-08-24T01:30:00+08:00`。这个字符串里的 `01:30` **就是作者当时所在地钟面上的时间**。

大量「git 工作时间分析」脚本的做法是取出 Unix 时间戳、按分析者所在时区换算——这在分布式团队里是错的：北京凌晨 1:30 的提交会被算成「伦敦前一天 17:30 的傍晚工作」，深夜信号被系统性抹掉。

本工具的立场：**不做任何换算，钟点字段原样使用**。每个人被自己的挂钟衡量：

- 北京 01:30 的提交 → 深夜（他当地的凌晨）
- 洛杉矶 17:30 的提交 → 白天（他当地的傍晚）
- 两者是**同一 UTC 时刻**，但属于作息不同的两个人——测试 `test_same_instant_two_wallclocks` 用钉死的双提交锚定了这一语义

周末判定同理走作者本地日期：UTC 周日 20:00 的提交对 +08:00 作者来说是周一凌晨——`test_weekend_uses_author_local_date`。

**author date 优先于 committer date**：author date 是「写下代码的时刻」，committer date 会被 rebase / merge / cherry-pick 搬运。量过劳要量写作，不量搬运（`test_author_date_wins_over_committer_date`）。

## 3. 信号与阈值：每一条都为防误报服务

| 信号 | 阈值 | 为什么是这个数 |
|---|---|---|
| late-night 窗口 | 22:00–04:59 | 21 点是许多团队的正常下班后；5 点是真正的黎明。窗口再宽，信号就被通勤加班稀释；再窄，漏掉 22 点的常态化。 |
| `LATE_NIGHT` | ≥ 15% | 每周 20 个提交里 3 个深夜。偶发赶工（一晚）到不了 15%，常态化（每周都有）必然超过。 |
| `WEEKENDS` | ≥ 20% | 每周五天工作日出勤 + 1 天周末 = 20%。即「每周固定牺牲一天休息日」是门槛，偶尔周六修个 bug 不算。 |
| `NO_BREAK` | streak ≥ 14 天 | 两周（含两个周末）无一日中断。真实项目冲刺一两周常见，三周以上连轴是身体的账单。 |
| `WEEKEND_LATE` | ≥ 3 个「周末深夜日」 | 单次可能是赶 deadline；三个不同的休息日各自燃到凌晨，是模式不是事件。 |
| 比例类信号样本下限 | 10 个提交 | **最重要的一条**。3 个提交 100% 深夜和 50 个提交 30% 深夜，前者什么都证明不了。样本不足，工具宁可沉默（`audit` 门禁的比例检查同此纪律，streak 是绝对计数不受此限）。 |
| `level` | 0 flag = ok / 1 = watch / ≥2 = alert | 单一信号有几十种无辜解释；多个独立信号同时出现，无辜解释需要连环成立——概率急剧下降。 |

阈值全部可以在 CLI 覆盖（`audit --max-late/--max-weekend/--max-streak`），因为不同团队的基线不同：4×10 小时轮班团队和朝九晚五团队不该用同一条红线。

## 4. 夜猫子辩护：trend 为什么是核心命令

对「深夜比例高」最有力（且完全正当）的反驳是：**「我就是夜里写代码，十年了，我喜欢。」**

这是真的，也是为什么绝对值不定罪。`trend` 的设计就是为了把「稳定夜型」和「模式改变」分开：

- 把作者自己的历史切成「最近 N 天」和「更早」两段
- 各算深夜/周末比例，比较差值（≥5 个百分点才算方向）
- Carol 型（一直凌晨，两段一致）→ **STABLE**：作息，不是事故
- Bob 型（白天基线 → 深夜化）→ **WORSENING**：燃烧开始的形状

判定要求每段 ≥10 个提交，否则 **INSUFFICIENT**——新人和短历史的作者不参与趋势游戏。

读报告的正确顺序：先看 `trend`（方向），再看 `authors`（现状），最后才看 `scan`（总量）。方向比位置重要。

## 5. 已知误报来源（与对策）

诚实的工具应当列出自己会错的方式：

| 误报源 | 机制 | 对策 |
|---|---|---|
| CI / 依赖机器人 | 机器不睡觉，深夜周末照常提交 | `--exclude-author "bot" --exclude-author "renovate"`（匹配姓名或邮箱） |
| 长尾 rebase | author date 保留原始深夜，一次性涌出 | 无害方向（不会凭空造深夜）；量的是 author 不是 commit 时刻 |
| 假期修 typo | 度假中顺手修一行 | 单事件，到不了 15%/20%；weekend-late 需 3 个不同日 |
| 双时区通勤 / 搬家 | 挂钟换了，作息没换 | 偏移记录在每次提交里，搬家前后各算各的，无需配置 |
| squash 合并 | 10 点 squash 凌晨写的 10 个提交 | 信号被低估（无害方向）；高 squash 仓库看 `--all` 分支上的原始提交 |
| 周休非周六日的文化 | 中东周休五六、部分国家周休四五 | 工具按周六日判定，对这些文化保守低估。**这是已知局限**，不值得为零依赖引入节日库——见 §7 |

## 6. 伦理边界（使用条款的灵魂）

这个工具可以用来救人，也可以用来监控人。边界如下，且写进了报告尾行：**signals start conversations, not verdicts**。

1. **默认自用**。最安全的使用者是照镜子的个人；其次是团队**知情同意后**的自我复盘（「我们都看看这季度是不是太狠了」）。
2. **绝不用于绩效**。深夜提交不是忠诚度指标，周末缺席不是懈怠证据。任何把本报告接进考核流程的用法都是对工具的滥用。
3. **点名之前先脱名**。会议材料里用 `--anonymize`；确认团队级信号真实存在后，再由本人决定是否对号入座。
4. **信号 → 对话**。alert 的正确响应是「最近是不是撑得太狠了？我能砍掉什么？」，不是「你深夜提交比别人多 12%」。
5. **数据不出机器**。纯本地运行，零上传，报告发出去之前经你手。
6. **这是证据之一，不是判决**。休假文化、on-call 轮值、时区错位都会污染信号——与当事人核对，永远是最后一步。

`audit` 子命令做 CI 门禁时同理：预算应当是**团队给自己**立的线（「我们的深夜比例不该超过 15%」），而不是管理层架在团队头上的摄像头。

## 7. FAQ

**Q: 为什么用提交时间而不是 push 时间？**
push 时间混合了 CI 节奏与批量操作，且大多平台不进本地 git。author date 是唯一每个克隆都自带、且绑定到个人的诚实字段。

**Q: 提交少的人（周末不提交，但周末都在工作）会漏报吗？**
会。本工具量的是「写代码的时刻」，不是「工作的时刻」。漏报方向（信号低估）比误报方向安全，接受。

**Q: 一个人改了系统时区，或者笔记本时区错了？**
每次提交独立记录偏移，改一次时区等于换一次挂钟，前后各算各的，无需全局假设。

**Q: 能不能检测「假期在干活」？**
技术上能（工作日历外的提交日），但节日历因国家/地区/公司而异，零依赖做不到普适。周末是最大公约数；更细的假期请用 `--since/--until` 手动圈出窗口自查。

**Q: 和这个仓库里其他点子的关系？**
同一族「git 考古 × 工程健康」工具，各挖一层：[gitweek](../gitweek/) 挖**做了什么**（被遗忘的工作）、[bus-factor](../bus-factor/) 挖**谁懂什么**（知识单点）、[todo-rot](../todo-rot/) 挖**欠了什么**（承诺债务）、midnight-oil 挖**何时在做**（人的燃烧）。四个维度合起来，是一次完整的团队体检。

**Q: 为什么 22:00–05:00 而不是 00:00–06:00？**
凌晨窗口会漏掉 22–24 点——恰恰是最常见的「下班后继续」时段。过劳的第一现场常在 23 点，不在 2 点。

**Q: 我扫出自己的仓库全是深夜，怎么办？**
工具作者扫了自己出生的仓库：5 个提交，100% 深夜，40% 周末（见 README 的 dogfood 一节）。第一步不是自责，是核对：这是冲刺（有终点）还是常态（没有终点）？前者设个结束日期，后者——把 `trend` 加进你的月度回顾，让 WORSENING 出现在你提离职之前。

## 8. 局限与未来方向

- **周休文化假设**：默认周六日为周末（见 §5 末行），对周休五六的文化低估信号。
- **提交 ≠ 全部工作**：会议、评审、on-call 不留提交。深夜提交是过劳的**充分样本**（存在即真实），不是**必要样本**（不存在不证明健康）。
- **可能的扩展**：假期日历插件（打破零依赖原则，故不内置）；per-repo 基线对比（同人跨仓库聚合，看总负荷）；quiet-period 检测（连续无提交天数作为**正面**信号——休息本身值得被看见）。
