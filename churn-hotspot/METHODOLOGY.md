# 变更热点 · 方法论与 FAQ

> 本文回答「为什么这样设计」以及每个阈值背后的理由。指标定义见 [README](README.md)。

---

## 1. 利息模型：为什么是 churn × size

把技术债想成一笔贷款：

- **churn（付息频率）**：一个文件每季度被改 N 次，就是每季度付 N 次利息。改它 = 读懂上下文 + 承担改坏的风险，每次都是真金白银的工程时间。
- **size（每次付息金额）**：改一行之前要读多少行。3000 行的文件改一次的上下文成本，十倍于 300 行的文件。

**score = churn × size 就是这个文件每季度支付的维护利息总额。** 单看任何一根轴都会排错：

- 只看 size：你会去重构那个 3000 行但两年没人碰的文件——没有改动的文件不付利息，它的债务是**零息**的；
- 只看 churn：你会去重构那个每周被改但只有 40 行的脚本——每次付息金额太小，总利息微不足道。

乘积最大的文件才是「每季度真实流血最多的文件」。这是 Adam Tornhill 在《Software Design X-Rays》中提出的经典 hotspot 分析（其前作《Your Code as a Crime Scene》首次引入），本工具是它的零依赖、可复现实现。

## 2. 为什么 churn 用「提交数」而不用「改动行数」

三个理由：

1. **抗大迁移污染**：一次全局改名的 diff 有 5000 行，用行数算 churn 它会淹没整张表；用提交数它只算 1 次。
2. **度量的本质是「多少人多少次需要理解它」**，而不是「产生了多少文本」。理解成本按「次」计费，不按「行」计费。
3. **可复现性**：提交数只依赖历史，不依赖 diff 算法对空白、重命名的处理细节。

## 3. 为什么 size 用「当前行数」而不用圈复杂度

圈复杂度需要对应语言的解析器，与零依赖目标冲突；行数是语言中立的复杂度代理（两者相关性在绝大多数代码库中足够强）。**承认局限**：一个 300 行的规整文件和 300 行的面条代码在这里同分。如果你需要更细的复杂度轴，把本工具的 JSON 输出与你自己的复杂度工具 join 即可——输出格式为此设计。

## 4. 创建 ≠ 债务：为什么 churn < 3 永远不进 RED/AMBER

一次性写就的 400 行文件只是「存在」，还没有「反复修改的记录」。它可能是未来热点，但**现在没有在付息**。MIN_HOT_CHURN = 3 要求一个文件先证明自己「被反复回头修改」，才有资格进入等级评定。这也自动防住了「大 feature 落地当天整包文件全 RED」的误报。

## 5. 等级规则：分位数 + 小仓库退化

- 热点文件（churn ≥ 3）≥ 5 个时：score 的 **P90 → RED，P75 → AMBER**（nearest-rank 分位）。用分位而非绝对阈值，是因为 500 文件的仓库和 50 文件的仓库 score 量级差两个数量级，绝对阈值只适合其中一个。
- 热点文件 < 5 个时：**分位数是伪科学**（P90 of 3 个数没有意义），退化为「最差的 eligible 文件 RED、其余 AMBER」。
- GREEN 不设下限——它就是「没有资格谈热点」的默认态。

## 6. 趋势规则：窗口平分与 3/1 阈值

窗口（默认 180 天）沿中点切成前后两半，比较两半的 touch 数：

| 前半 | 后半 | 判定 | 行动建议 |
|---|---|---|---|
| ≥3 | ≥3 | **PERSISTENT** | 计划专项重构——这是复利债务 |
| ≤1 | ≥3 | **EMERGING** | 立刻介入（补测试、做拆分），趁它还便宜 |
| ≥3 | ≤1 | **COOLING** | **不要投重构预算**——它正在自愈 |
| 其他 | 其他 | STABLE（churn ≥ 3 时） | 观察 |

3/1 阈值与 MIN_HOT_CHURN 呼应：「热」的定义统一为 ≥3 次，「冷」的定义统一为 ≤1 次，中间地带（2 次）既不点火也不熄火。**COOLING 是本工具最反直觉的输出**：score 全库第二的热点可能正是最不该重构的文件（见 README 样例中的 legacy 文件）。<!-- dd:ignore: 指 demo 虚构文件，样例见 examples/ -->**EMERGING 则是分数原理性看不见的**——新火情的分数还没涨起来，只有时间轴能抓到它。

## 7. 默认排除：churn 的三类噪音

| 类别 | 模式 | 为什么排除 |
|---|---|---|
| lockfile | `package-lock.json` 等 lock 家族 | 它们的 churn 由依赖更新驱动，与设计质量零相关，但频率极高（CI 每天都可能碰） |<!-- dd:ignore: 模式名提及，非具体文件引用 -->
| vendored / 构建产物 | `node_modules/`、`vendor/`、`dist/`、`target/` 等目录 | 不是你写的代码，重构它没有意义 |
| 生成代码 | `*.min.js`、`*_pb2.py`、`*.pb.go`、`*.generated.*` 等 glob 模式 | 源头在上游，改产物不改根源 |<!-- dd:ignore: glob 模式提及，非具体文件引用 -->

追加用 `--exclude GLOB`（可重复，glob 含 `/` 时匹配整条相对路径，否则匹配文件名或任一路径段）；全部关闭用 `--no-default-excludes`。二进制文件（前 8KB 含 NUL）不靠模式而靠内容检测，自动跳过。

## 8. FAQ

**Q: merge commit 里的改动会漏算吗？**
不会漏改动本身。`git log` 默认遍历全部可达提交，分支上的每个提交都会带着自己的文件列表出现；merge commit 本身不带 diff，但它的改动早已按提交逐个计入（已用真实 merge 仓库验证）。两个已知低估场景：冲突解决记在 merge commit 上的手工修改（该 diff 默认不显示）；以及 squash-merge 到主干后分支被删除——squash 出的提交正常计入，无损失。

**Q: 为什么不用 `git log --since` 做窗口过滤？**
因为它是**遍历剪枝**不是日期过滤：从 HEAD 回溯遇到第一个窗口外的提交就停止走历史。一旦提交日期交错（rebase、backport、导入的历史），窗口内的提交会被静默丢弃。本工具首次 dogfood 时被这个坑咬过（60 天窗口扫出 0 文件），修复方式是全量拉取、解析侧按日期过滤。同理，Python 的 `str.splitlines()` 会把 `\x1e`（RECORD SEPARATOR）当换行符，记录分隔不能用 `splitlines()` 而必须 `split("\x1e")`——这两个坑都以注释形式留在了 `collect()` 里。

**Q: `git mv` 之后历史会丢吗？**
不会。`--name-status` 输出 `R100<TAB>old<TAB>new`，构成 rename 映射；touch 归账时沿链解析（a→b→c 传递归到 c），改名前的全部历史落在当前路径上。

**Q: 为什么默认窗口 180 天？**
一个季度多一点：短窗口（30 天）会被单个冲刺放大成「全员热点」，长窗口（365 天）会稀释掉最近的趋势变化。趋势轴依赖窗口平分，180 天 = 每半 90 天 ≈ 一个季度，正好是「上一季度 vs 本季度」的对比口径。用 `--window` 调整。

**Q: 分支历史（未合并的 feature 分支）算吗？**
默认 `git log` 只遍历当前分支的可达历史（HEAD），未合并分支不参与——热点应该反映「实际在主干上发生的维护成本」。

**Q: 能不能把 score 和我自己的复杂度工具 / 覆盖率数据 join？**
可以，`--format json` 的输出字段（path / churn / lines / score / trend / old_churn / recent_churn）就是为此设计的稳定接口。

**Q: 大仓库性能？**
一次全量 `git log --name-status`。十万提交级仓库在秒级到十秒级；更大的仓库建议在浅克隆（`git clone --depth` + 需要的窗口）上运行。

**Q: 阈值能调吗？**
所有常量集中在 `churn_hotspot.py` 顶部的常量区（`MIN_HOT_CHURN`、`RED_QUANTILE`、`AMBER_QUANTILE`、`DEFAULT_WINDOW`、`DEFAULT_EXCLUDES`），有注释、可整体替换。

## 9. 已知局限

1. **行数是复杂度的代理**，不是复杂度本身（见 §3）；
2. **copy（`C` 状态）不建 rename 链**，只把 touch 归到新路径——copy 场景罕见且语义本就模糊；
3. **生成代码识别靠模式匹配**，命名不规范、不在默认清单里的生成文件需要 `--exclude` 手工补；<!-- dd:ignore: 模式名提及，非具体文件引用 -->
4. **等级基于分位数**，极端单调的仓库（所有文件 churn 都是 1）会正确地全员 GREEN。

## 10. 系列定位

newidea 点子实验室的第 6 件作品。前 5 件（决策债务 / gitweek / 文档漂移 / 知识单点 / 承诺锈蚀）回答「哪里有问题」；本件回答「先修哪里」。与 bus-factor 互补：bus-factor 找出「只有一个人懂的文件」（知识风险），churn-hotspot 找出「值得更多人懂的文件」（维护成本）——两张表做交集，就是配对 review / 结对重构的优先级清单。
