# 数字阁楼 · Digital Attic

> 相册是这个时代唯一不被记账的仓库：拍进来的每一张都有登记，被再看的没有一张有记录，而「存储空间不足」是它唯一递达的账单。
> The camera roll is the only warehouse nobody audits: everything gets checked in, nothing gets checked on, and "Storage Almost Full" is its only invoice.

---

## 一句话

拍摄成本趋近于零、删除成本（决策痛）居高不下，媒体库于是只进不出、单调膨胀，而系统只在爆满时说话，且只给一个「管理存储空间」按钮——不给结构。3300 张截图、几十簇连拍废片、几百张聊天缓存图和真正的回忆混在一起，看起来一样、权重一样；152 段视频少而重、占着大头房租，排序却只按时间不按体积；「存进去 = 再也不看」无人量化，但每 GB 的房租照付。本件把媒体库当成一个国家做**人口普查**：`scan` 扫描目录抄录账本，出生日期优先**从文件名考古**（IMG_20230521、Screenshot 2026-01-05、截屏20260105、WX20260105、VID_20250214、微信图片_20231102……文件自己记得自己是哪天生的），考古不出才用 mtime 兜底并标注来源；census 出**身份构成**（照片/视频/截图/连拍/聊天缓存五类，字节贡献加总恒等于总字节）、**库龄双尺**（按件数中位 3.2 年 vs 按字节中位 1.9 年——新的重，老的轻）、**只进不出**（近 12 个月 vs 前一年新增）；`junk` 点名**垃圾三匠**并钉死本件的招牌分裂——示例库 1,273 件里垃圾 644 件（**50.6% 件数**）却只有 933 MB（**0.3% 字节**）：删垃圾省不下房租，省的是每一次翻找；`rent` 把字节折成房租（--price/--quota，不发明单价），303 GB 在 2 TB 档 = ¥10.06/月，其中视频独占 99.1%；`simulate` 算瘦身推演但**永不执行删除**——垃圾三匠全部出库，库存省 0.3% 字节、房租省 ¥0.03/月、翻找的陪跑少一半；而「全部视频」出库，房租 ¥10.06 → ¥0.09/月，**大房东一走，垃圾露出原形**（幸存库字节口径 0.3% → 34.3% 翻红）——两把尺子分开量，才不会得出「删垃圾没用」或「全是视频的错」这类半截结论。

## 它解决谁的、什么场景下的、什么问题

| 维度 | 说明 |
|---|---|
| **角色** | 手机 256 GB 用了 250 GB、每月被「存储空间不足」弹窗羞辱的人；每月为 2 TB 云端套餐付费、却说不清里面装着什么的人；承诺「今年把照片整理好」第五年的人；想给父母那 4 万张照片做个了断、又怕误删孤本的人。 |
| **场景** | 存储告警弹出的那一刻（被迫现场微操，删哪个都心疼）；续订 iCloud/网盘会员之前（「我为这 2 TB 付的年费里，多少在为垃圾交租」）；换新手机/新电脑之前（300 GB 迁移之前想先瘦身）；年底心血来潮打开相册、翻了两千张就放弃的那一刻。 |
| **问题** | ① **只进不出从不记账**：库存单调膨胀，没有任何账本记录增长率，更没人预测「什么时候爆」；② **告警是唯一账单**：系统只在你爆满时说话，且只给一个按钮，不给结构——你永远不知道该删什么；③ **垃圾没有名字**：截图、连拍废片、聊天缓存混在回忆里，看起来一样、权重一样，每次翻找都要陪跑；④ **房租付在看不见的东西上**：视频少而重占大头字节，排序只按时间不按体积，「为垃圾交的租」和「为视频交的租」从没被分开过；⑤ **只量一把尺子**：只看件数会得出「过半是垃圾，这库没救了」，只看字节会得出「删垃圾省不了几个钱」——两个结论都是半截的。 |
| **价值与意义** | ① **文件系统即账本**：不要求你手编 TSV——照片库本身就是账本（`scan` 一次抄录，之后所有命令对账本做算术）；② **出生日期考古**：优先从文件名解析拍摄日期（13 种真实命名模式），文件被拷贝多少次都记得自己是哪天生的；考古不出才用 mtime 兜底，且账本永久标注来源——**带来源的日期才是诚实的日期**；③ **五类身份 + 字节恒等式**：每个文件有且仅有一个主身份，字节贡献分解加总恒等于总字节（残差 0，测试钉死）；④ **双口径门禁**：垃圾件数 > 50% 或垃圾字节 > 30% 各自独立亮红灯——两把尺子各量各的，谁越线谁说话；⑤ **连拍指纹**：账本只有日期粒度，「同一分钟」不可得，但同一批连拍的文件名尾部序号是**秒级连续**的（相邻差 ≤ 60），一天里随手拍的多张序号跳变巨大——分组按「同目录+同名基+同日」，定簇靠连续游程，两张相似是生活，三张相似才是连拍；⑥ **simulate 永不执行删除**：账本只算术，删与不删永远是人的决定。 |

## 核心思想：把「存储空间不足」换成一张人口普查表

| 概念 | 规则 | 回答的问题 |
|---|---|---|
| **出生登记** | 文件名日期考古优先（`name`），mtime 兜底（`mtime`），账本永久标注来源 | 「这件是什么时候进库的？这个日期可信吗？」 |
| **身份构成** | screenshot > chat > burst（全库互查）> video > photo，五类互斥，字节加总=总字节 | 「这间阁楼里住的都是谁？」 |
| **库龄双尺** | 按件数中位 vs 按字节中位 | 「库在变老还是在变重？」——两把尺子的方向差就是答案 |
| **只进不出** | 近 12 个月 vs 前一年新增件数；账龄不足两年免判 | 「库在加速生长吗？」——匀速也照样爆，增长率再平也是单调膨胀 |
| **垃圾三匠** | 截图 / 连拍与成批 / 聊天缓存，件数与字节双口径 | 「每次翻找的陪跑者有多少？他们占多少房租？」 |
| **房租账** | 字节 × (月费 ÷ 套餐 GB)，垃圾租与视频租单列；不给套餐就不发明单价 | 「这个看不见的仓库每月烧多少钱？谁是大房东？」 |
| **瘦身推演** | --prune 六种口径，算完就停，永不执行删除 | 「如果删了，省多少字节、多少房租、中位库龄怎么变？」 |

三条设计立场刻在实现里：**门禁是双口径的**——垃圾件数过半或垃圾字节超三成，任一越线即 RED exit 4，因为两把尺子量的是两种痛（翻找的陪跑 vs 字节的房租）；** burst 的判据是序号连续性而不是时间戳粒度**——账本的出生日期只有天，「同一分钟」在账本路径上不可得，但连拍的命名指纹（尾部序号秒级连续）骗不了人，跨分钟的连拍会被拆散——宁可漏报不误报；** aged ≠ 该删**——推演报告自带横幅：老照片往往是唯一的孤本，算术不是建议。

## 安装（零依赖）

只需 Python 3.8+，无需 `pip install` 任何东西。

## 账本格式

`scan` 从目录抄录，也可手编。TSV，每行 = 一件媒体：

```
name	path	bytes	birth	mtime	source
IMG_20230521_143022.jpg	2023/	3456789	2023-05-21	2023-05-21	name
DSC_00001.JPG	imported/	2987654	2019-08-14	2019-08-14	mtime
VID_20250214_193045.mp4	2025/	1875000000	2025-02-14	2025-02-14	name
```

- `name/path/bytes/birth` 必填，`mtime/source` 可选（`-` 占位；手编省略 source 时默认 `name`）；
- `source` = `name`（文件名考古）/ `mtime`（时间戳兜底）——**来源是这个账本最诚实的一列**：mtime 兜底占比超三成时 `validate` 会提醒你，这部分库龄是估的（拷贝会重置时间戳）；
- 分析只用 `birth`，`mtime` 仅存档作证据；坏行带行号 exit 2（列数 / bytes 非整数或为负 / birth 缺失或非法或在未来 / source 非法 / 同目录重复登记）。

## 命令速查

```bash dd:ignore
python3 digital_attic.py scan ~/Pictures -o attic.tsv          # 目录普查登记（寄居户/非媒体不入账）
python3 digital_attic.py census attic.tsv --today 2026-09-01 --price 68 --quota 2048   # 全库普查（红灯 exit 4）
python3 digital_attic.py pyramid attic.tsv                     # 库龄金字塔：库长什么样一眼可见
python3 digital_attic.py junk attic.tsv --today 2026-09-01     # 垃圾三匠明细 + 字节恒等式
python3 digital_attic.py rent attic.tsv --price 68 --quota 2048                        # 房租账：谁是大房东
python3 digital_attic.py simulate attic.tsv --prune junk --price 68 --quota 2048       # 瘦身推演（永不执行）
python3 digital_attic.py validate attic.tsv                    # 账本体检：出生来源占比、同名披露
```

## 一个真实样例

小陈 2019 年有了第一部能拍照的手机，到 2026 年 8 月，相册 1,273 件、302.9 GB，iCloud 2 TB 档 ¥68/月。每次「存储空间不足」他都现场删几张最近的照片，删完两周就又满了——因为他删的永远是**最新也最小**的那批。2026-09-01 他做了一次普查（`census`，exit 4）：

```
数字阁楼普查 · 1,273 件 · 302.9 GB（2019-01-01 → 2026-08-30）

  出生登记      文件名考古 1,261 件（99.1%）· 时间戳兜底 12 件（0.9%）
  库龄          按件数中位 3.2 年 · 按字节中位 1.9 年——新的重，老的轻
  身份构成      照片 477 / 视频 152 / 截图 330 / 连拍/成批 224 / 聊天缓存 90
                字节  照片 1.8 GB / 视频 300.2 GB / 截图 517 MB / 连拍/成批 335 MB / 聊天缓存 81 MB
  只进不出      近 12 个月新增 207 件，前一年 173 件（+19.7%）——库在加速生长；删除行为不在普查视野里，只进不出是默认命运
  垃圾三匠      截图 330 件 517 MB · 连拍/成批 224 件 335 MB · 聊天缓存 90 件 81 MB
                合计 644 件（50.6% 件数）· 933 MB（0.3% 字节）
                件数口径是多数、字节口径是少数：删垃圾省不下房租，省的是每一次翻找
  房租          302.9 GB × 0.0332 元/GB/月（¥68 ÷ 2048 GB）= ¥10.06/月 · ¥120.7/年
                其中垃圾房租 ¥0.03/月 · 视频房租 ¥9.97/月（99.1%）

判定 RED —— 垃圾件数占比 50.6% 过半（门禁 50%）：这半个库的每次翻找都在陪跑；junk 看明细，simulate 算推演，删与不删仍是人的决定
```

三本账读过之后：**每次翻找，二分之一的概率在给垃圾陪跑**（`junk`：截图 330 件中位库龄 2.9 年——截图在阁楼里活不过新鲜劲儿，但一张都不走）；**删光全部垃圾，房租从 ¥10.06 到 ¥10.03**（`simulate --prune junk`——省 0.3% 字节，但幸存库翻绿，以后每次翻找都不再陪跑）；**真正的房东是视频**（`rent`：152 件视频占 99.1% 的房租；`simulate --prune videos`：房租 ¥10.06 → ¥0.09/月，而大房东一走，幸存库的垃圾字节占比立刻从 0.3% 翻红到 34.3%——**两把尺子分开量，才知道谁在替谁打掩护**）；至于「把 2019-2021 的老照片清了」——`simulate --prune aged --years 5`：304 件只占 1.5 GB（0.5%），横幅写着「aged ≠ 该删——老照片往往是唯一的孤本」。最后他给父母库做扫描时只用了 `scan`：账本是一份 TSV，报告不回显任何绝对路径。

## 诚实条款

普查数库存结构，不读心：atime 在绝大多数文件系统上不可靠，本件**永不假装知道你看过哪些照片**——「存进去就再也不看」是现象的命名，不是被测量的结论。mtime 兜底的出生日期在文件被拷贝、迁移、云同步后会失真，账本因此永久标注每一行的来源，mtime 占比过高时主动提示「这部分库龄是估的」；重复照片检测需要读文件内容，超出普查范围，validate 只对同名异目录做披露；连拍判定按「序号秒级连续」的命名指纹，跨分钟的连拍会被拆散、成批导出会与连拍同簇——宁可漏报不误报，且「连拍/成批」这个身份名本身就承认了二义性。房租按你给的档位线性折算，实际计费是档位制，库超档时横幅披露。它不删任何东西：simulate 的每一个推演都只是算术，aged ≠ 该删，删与不删，永远是人的决定。

## 边界

- **纸盾 · Paper Shield** 管备份的信任（存不存在、可不可信、回不回得来），本件管库存的结构（住着谁、多老、多重、房租多少）——同一个库，两本账。
- **稍后永不 · Later Never** 管注意力消费的行为（收藏了读不读），本件管媒体库存的本体（占多少、住着谁）——一个管决策，一个管仓库。
- 手机相册的专有库（HEIC 原图、Live Photo 配对、iCloud 优化存储的占位符）建议先导出到目录再 `scan`；账本格式是公开 TSV，任何能导出清单的工具都能喂饱它。
