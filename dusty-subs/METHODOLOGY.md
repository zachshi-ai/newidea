# METHODOLOGY · 订阅账本学

> dusty-subs 的每一个数字都来自确定性规则，每条规则都值得被追问动机与边界。本文记录三道关的设计推导、诚实条款与已知局限。

## 1. 立场：翻译价格，不审判消费

月费是订阅经济最成功的一项设计：它把价格切成大脑不设防的小块，再把扣款藏进你不会看的账单里。行为经济学称之为**支付的解耦**（decoupling）——消费的快感与支付的痛感被自动续费隔开，大脑只对「掏钱动作」记账，于是订阅在你的心理账本上根本不存在。

dusty-subs 只做一件事：**把两个定价单位之间的汇率建起来**。订阅按月报价，生活按次发生；cost per use 不是道德分数，是把「30/月」翻译回「你每次实际付出多少」的汇率。翻译完成之后砍不砍，是你的决定——工具的立场停在翻译：健身房不审判你，账本也不，账本只是让 1,760/次 这个数字无法继续假装自己是 299/月。

## 2. 三道关的推导

**名字关。** 流水里的商户描述是给风控系统看的，不是给账本看的：`NETFLIX.COM 8665797172` 与 `NETFLIX.COM 4029357733` 是同一个商户的两次扣款。归一化规则：小写；抹掉 ≥2 位的数字串（订单号、电话、卡尾、`12月` 之类的月份戳——它们都有共同特征：**数字连排**）；标点变空格后折叠。单数字保留（`PS PLUS 3 MONTH` 不该变成 `ps plus month`）。代价：`IPHONE 12 PLAN` 与 `IPHONE 14 PLAN` 会撞成一个商户——用词骨架区分商品的数据世界 v1 不救（见 §6）。

**节奏关的两层。** 缺缴是真实世界的常态：账户余额不足、主动暂停一个月、银行系统抽风。设中位间隔 m：

- **缺一个月**制造一个 ~2m 的大间隔。实测月付钉同日的真实日历：正常间隔在 28/30/31 之间摆动，缺缴月的间隔比（61/31 ≈ **1.97**）稳定落在 2.05 以下；
- **缺两个月**的间隔比（92/31 ≈ **2.97**）远超 2.05，而且通常伴随间隔方差的全面崩坏。

于是阈值定在 **2.05**：单月缺缴活着，连缺两月出局。这比只看变异系数（CV）可靠——缺一个月的 CV 在真实日历下是 0.344，贴着 0.35 的线，换个月份分布就会误杀。CV 仍在第二层值守：它拦的是**没有大洞但持续 jitter** 的序列（25、35、25、35 交替）。真正的大洞由第一层用更可读的语言报告：`gap 130d is a 2.8x outlier against median 46d` 比一个 cv 数字更能让人看懂为什么打车不算订阅。

**金额关。** 间隔规律 + 金额规律才是订阅；间隔规律 + 金额狂野是**生活方式**（每周菜钱、每月大采购）。判据刻意宽松：只要 ≥60% 的扣款落在中位金额 ±20% 以内即通过——订阅会涨价（62→70），涨幅会在 ±20% 带内存活 11 期；但散金额的采购几乎不会恰好有六成落在带内（样例里的盒马：17%）。

**min-hits = 3。** 两次扣款无法区分「订阅」和「你两年买过两次的东西」。第三次的缺席比第三次的出席更能说明问题。

## 3. 三条诚实条款

1. **预测锚定流水末日，绝不碰墙钟**。未来 12 个月的日历从流水的最后一笔推起——同一份 CSV 永远得到同一份报告。这让样例可复现、测试可断言，也让「报告的年龄」变得诚实：导出之日起算一年，而不是一个会漂移的「今天」。
2. **拒绝的如实列出，不黑箱**。每个被三道关拦下的商户都带着可读的理由出现在 `periodic-looking, but failed the checks`：它有几次扣款、周期看起来是多少、死在哪条规则上。工具对你隐藏的唯一东西是它没看见的东西（< min-hits 的一次性消费，以计数示意）。
3. **数据的瑕疵入账不吞没**。重复行去重并计数（真实导出常有窗口重叠）、坏行跳过并计数、收入行按类型列或负号排除——每一笔被丢弃的数据都在报告开头留了痕。账本的第一美德不是全，是真。

## 4. 边界情形的处置

| 情形 | 处置 | 理由 |
|---|---|---|
| 房租、水电、物业 | 照常入册（它们**是**周期承诺），`--ignore` 负责请出去 | 年化视角对「你住在里面的订阅」同样成立；工具不替你决定什么值得看，`--ignore` 的正则就是那个决定 |
| 同商户两个订阅（如视频网站的月卡+年卡同扣） | v1 合并成一个商户，间隔与金额大概率因此破规，整组出局 | 保守方向：错杀一组好过错并两笔账；拒绝理由会提示你去解释里看时间线 |
| 同一天两笔扣款 | 计入 hits；间隔计算只在**不同日**之间进行 | 同日双扣是真实现象（补扣、升级），它不该伪造出 0 天周期，也不该被吞掉 |
| 付款日随周末漂移（3 日扣款漂到 5 日） | 名字关照常聚合，节奏关照常通过（±2 天远在 2.05 之内），月付预测钉住**最后一次**的实际付款日 | 银行的便利不是用户的错；预测宁可继承最后一次的现实 |
| 预付费年卡只买过一次 | min-hits 之下，不出现 | 一次购买是历史，不是承诺 |
| 金额为 0（试用未续） | 0 也在金额带上，0 扣款周期规律可入册 | 但价格痕迹会把「降到 0」报为 drop——降级与弃用值得被看见 |
| 描述词骨架会变的商户（城市名、门店号进词） | 撞成多个假商户，各自 hits 不足，全体出局 | 归一化只救数字与标点；词骨架是商户自己的指纹学，v1 不猜（`--ignore` 救不了它，等待 §6 的白名单） |

## 5. 与仓库其他点子的差异

「对未来的承诺是一种负债」是这个仓库反复出现的世界观：todo-rot 看代码注释里的承诺半衰期，decision-debt 给悬而未决的决策计息。本件共享这个世界观，但换了整个领域与数据源：**个人财务**，账本从 git 换成银行流水。仓库扩容后消费账本类近邻渐多，边界如下：

- **cost-per-wear（每穿成本）** 量**持有端**利用率——衣服买回来之后穿没穿（吊牌价÷穿次，静态快照）；本件量**持续付费端**——服务每 31 天自动扣一次钱（流水周期检测，动态账本）。两件共享「除以使用次数」的翻译思想，但一个的敌人是闲置的衣柜，一个的敌人是自动续费。
- **ghost-login（僵尸账号）** 管账号的安全暴露面；本件管还在扣费的服务。僵尸账号是「忘掉的注册」，吃灰订阅是「忘不掉的扣款」。
- **slow-leak（暗漏）** 读的是物理用量（度、吨、立方米）找泄漏；本件读的是金融流水找周期承诺。一个是房子的心跳，一个是钱包的脉搏。
- **felt-inflation（体感通胀）** 量同一篮子东西的价格变化；本件量篮子里那些「你忘了自己在买」的成员本身。
- **recoup（回血）** 管闲置物的处置变现，本件管在续服务的去留——幻想价对吃灰价。
- **cart-line / want-ledger** 管单次购买的决策（这单该不该发生、怎么付得聪明）；本件管已经发生的购买的未来（下一年还要被扣多少）。

## 6. 已知局限

- **使用次数依赖手工申报**。cost per use 的分母来自你手写的 usage 清单——这是特性不是缺陷（任何「自动统计使用」都意味着监控你自己），但意味着分母的诚实度由你决定。工具只保证分子（年化成本）是流水里的硬事实。
- **退款、退货、争议扣款不在 v1 范围**：它们会作为一笔独立扣款（正负号视导出格式）被名字关聚合或被金额关拒绝。误入的退款会让某期金额掉出金额带——最坏结果是整个组被拒绝（保守方向），不会算出负订阅。
- **多币种混排**：金额被当纯数字。美元年费与人民币月费混在一份流水里时，年化排行是错的可排序的错——分币种导出是用户的活。
- **归一化是指纹学不是语义学**：它认得 `8665797172` 是噪声，认不得 `LosAngeles` 和 `Seattle` 是同一家的两家分公司。词骨架变化的商户请等 v2 的白名单（`--alias Netflix=netflix`）。
- **家庭/共享套餐的次数归属是哲学问题**：全家共用的视频会员，使用次数算谁的？工具的立场：usage 清单是你的，你填家庭总数它就是家庭成本。

## 7. FAQ

**Q: 为什么 mpu 默认 15，判定线是 3×？**
15 是「一次顺手消费」的心理阈值量级：一杯咖啡。≤ 一杯咖啡/次的订阅是生活的一部分；1–3 杯之间值得每季度重新想一次；超过 3 杯，你的每一次使用都在为吃灰的部分付钱——那不是订阅，是税。三个数字全部可调（`--mpu`），阈值不是科学，是让你开始计算的那声闹钟。

**Q: 年化成本和下一年锁定额为什么不相等？**
年化 = 末次金额 × 365 ÷ 中位间隔，是**比率**（把不完整的年份拉直到 365 天）；锁定额 = 预测日历里真实会发生的笔数 × 金额，是**存量**（下一年实际会被扣走多少）。月付订阅年化略高于锁定（365/31 ≈ 11.8 期 vs 实际 12 期边界差异），年付订阅两者近似。看趋势用年化，看现金流用锁定。

**Q: 银 app 不是已经有「自动分类」了吗？**
银行分类的是**单笔交易**（这笔是「生活服务」），从不分类**时间模式**（这个商户每 31 天扣我一次、持续了三年、下一年还要扣我 12 次）。周期性是时间轴上的属性，单笔分类在原理上就够不着它。另外：把流水交给银行 app 的分类器，和在自己机器上跑 700 行标准库 Python，隐私代价不在一个量级。

**Q: 为什么不自动抓取支付宝/银行 API？**
因为「零依赖、纯本地、不上传」不是交付形态的巧合，是这件点子的立场：银行流水是最敏感的个人数据。任何为了省一次导出而引入的 API 依赖，都会把这份账本变成又一份上传到别人服务器的数据。导出 CSV 的十分钟，是这件事应有的摩擦。

**Q: 和 todo-rot / decision-debt 有什么不同？**
见 §5。一句话：它们管代码里的债，本件管生活里的自动扣款——共享「承诺即负债」的世界观，互不共享任何数据与领域。

**Q: 我月月都用，cost per use 低到尘埃里，为什么还上账本？**
keep 不是勋章，是豁免。账本的职责是让 cut 的现形，keep 的可以继续过安心日子——但年化排行和下一年日历对 keep 的同样生效：**用得起**和**下一年还想不想被锁定 10,498** 是两个问题，工具把两个数字都给你。
