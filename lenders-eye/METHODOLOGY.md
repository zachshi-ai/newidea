# METHODOLOGY · 银行眼

## 1. 为什么「结清了」不等于「没事了」

征信档案记的是**账户的生命史**,不是你此刻欠多少钱。一笔网贷结清后,账户记录(开户日、额度、放贷方)仍然留在档案上——银行审批员看到的是「他曾经缺钱到要借网贷」,而不是「他现在不欠了」。这就是本件把 `settled` 单列成一种状态、把 SETTLED-GHOST 做成一盏黄灯的原因:**账户的痕迹是历史,余额才是现在,而审批两样都看**。

通识口径(可翻案):结清 + 向平台申请关闭/销户,让账户从「结清未销户」变成「已销户」——痕迹的性质才从「活跃的网贷用户」变成「历史」。

## 2. 硬查询:你亲手按下的扣分键

每次机构以「贷款审批」「信用卡审批」「担保资格审查」为由查你的档案,报告上就多一行,且**近期的密集查询本身就是负面信号**——它会被解读为「他在到处找钱」。而大多数人对硬查询毫无感知:点一下「查看我的额度」、点一下「开通白条」,背后可能就是一次硬查询。

窗口口径本件钉成两扇:61 天(近 2 月,线 3)与 183 天(近半年,线 6)。设计上的两个立场:

- **短窗看冲动,长窗看习惯。** 样例账本短窗 2 笔、长窗 7 笔——「近两个月已经收敛,但半年的账还在」。两扇窗分开报,才能把「已经刹车」和「历史欠账」分开说。
- **软查询永不进窗。** 贷后管理、个人自查不构成信号,这也是为什么自查免费且不伤征信——账本从解析层就把它们分开,不设 hard 列,由 reason 推导,报告写了什么就是什么。

## 3. 额度使用率:银行的情绪表

使用率 = 信用卡欠额 ÷ 信用卡总额度。通识口径:≤30% 优、≤50% 良、≤80% 警、>80% 危——「刷爆的卡在审批员眼里是『这人缺钱』」。两个口径细节:

- **加总口径**:多卡合并算总使用率(样例钉死:50,000+50,000 额度、40,000+20,000 欠额 = 60.0%),单卡刷爆另说——本件取加总,因为总盘子才是「缺钱程度」的信号。
- **恰线不亮**:80.0% 不亮红灯只挂黄档——宁可少报一个点,不多冤枉一分钱。浮点实现上用 `> line + 1e-9`,86.4% 这类数字逐字钉进测试。

## 4. gate:窗口随申请日滚动

`gate` 与 `report` 的唯一区别是「今天」是谁:`report` 用 as-of(档案视角的现在),`gate` 用 `--apply-date`(假设那天申请,两扇查询窗与逾期窗全部滚到那天)。于是「等到 12 月再申请会怎样」不是一个猜测,而是同一台引擎换一个日期重跑:

- 12-01 视角:长窗只剩 4 笔(7 月前的查询自己滚出去了)、逾期 delta 741 天出窗——**时间已经治好的两盏灯自动变绿**;
- 剩下的 FAIL(白条在贷、使用率)与日期无关——**钱的问题不会随时间消失**。

这就是 clock 的理论依据:**把五盏灯按「 heal = 时间」与「heal = 钱」分成两半**。查询与逾期住在滚动窗里,出窗日是闭式解;余额与销户住在账面上,不动手永远在那里。

## 5. 愈合日的闭式解与一个真 bug

查询窗的愈合:窗内 k 笔、线 L,需要最老的 (k−L) 笔出窗,heal = 第 (k−L) 老笔的日期 + 窗宽。逐日扫描是独立第二路径(validate/测试对拍)。

对拍抓出的真 bug 在逾期侧:灯的语义是「窗内**存在** 30+ 天逾期」,所以愈合要求窗内**清空**——而**更老的逾期先跨过 730 天线,最新的那笔最后出窗**,heal = 最新在窗逾期日 + 窗宽。初版闭式解取了最老一笔,样例账本只有一笔在窗内、永远暴露不了,**11 笔 + 2 笔逾期的多笔构造当场抓住**——「构造已知真值的合成账本」与「双路径对拍」第 N 次物有所值。

## 6. 为什么 lender 是列、type 不是判据

「花呗算不算网贷」在产品名层面永远吵不清——本件把判定交给 `lender` 列:**钱从 online 平台来的,就是 online 敞口**,不管你把它记成 credit_card 还是 online_loan。产品名是营销,放贷方是事实。与之相反,MULTI-LENDER(多头)刻意排除信用卡:循环账户是信用卡的正常形态,三张卡不是多头,三个贷款平台才是。

## 7. 零墙钟与时间机器

as-of 缺省 = 三本账所有日期的最大值(档案的「现在」就是你最后一次抄录的那天),`--as-of` 钉死任意日期回放。源码无 `date.today` / `datetime.now` / `time.time`,同账任何机器任何一天逐字节一致。时间机器的用途是历史的而非未来的:`--as-of 2026-06-30` 看半年前——那时钱的问题已经三盏红,而查询的债一笔都还没欠下。**档案上每一步都有日期,只是从来没有人替你回头看。**

## 8. FAQ

**Q:为什么不直接连央行征信接口?**
征信中心没有对个人的开放 API;每年 2 次免费自查(线上简版/线下详版)是官方渠道,抄录十行是全部数据工程。而且「手抄」本身就是一次亲眼看档案的仪式——本件反对的是从未看过,不是抄录的辛苦。

**Q:「综合评分不足」到底差在哪?**
没人能完全回答——那是审批模型的黑箱。本件能做的是把**档案侧**五个看得见的信号摆出来:红灯是你在申请前还能改变的,绿灯排除档案侧的嫌疑,剩下的(收入、流水、房屋本身)带去问客户经理。

**Q:我要不要先销掉所有信用卡「洗干净」档案?**
本件不管这个决定,只给一个事实:账本上 `closed` 的账户从所有灯里消失——但「信用历史长度」这类本件不建模的信号,行业通识里反而喜欢老账户。销不销,信贷经理说的永远赢。

**Q:多久抄一次账?**
每年两次免费自查时顺手。查询窗 183 天、逾期窗 730 天——半年一抄的粒度足以让所有窗口的答案误差不超过一次自查周期。

**Q:这是「征信修复」服务吗?**
不是。时间和小额结清是仅有的两种合法修复;本件不删任何记录、不认识任何「内部渠道」,只把「时间能治到哪天、钱能治到几成」算清楚。
