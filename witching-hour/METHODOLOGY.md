# METHODOLOGY · 缺陷出生时间学

> witching-hour 的 RR 不是修辞，是一套有分母有样本量的归因统计。本文记录每一条归因规则的动机、边界与已知局限。

## 1. 两条时间线：归因给出生，不归因给发现

每个缺陷有两个时刻：**引入**（那行代码被写下的瞬间）与**发现/修复**（fix commit 落地）。CI、周报、事故复盘全部围绕第二个时刻运转——因为它是显式的、有工单的。但责任在第一个时刻：竞态条件不是 code review 发现它的那个上午诞生的，它诞生于写下它的那个凌晨。

工具的归因链：`git diff --unified=0 <fix>^ <fix>` 找出被删除/修改的旧行（嫌疑行）→ `git blame <fix>^ <file>` 找到每行的出生 commit → 出生 commit 的作者钟点入桶。一阶归因，不递归：如果一行 bug 上一周刚被另一个 fix 写坏过，它归因给那个 fix 的时刻——链式追溯的边际收益递减，且会把同一个缺陷重复计票。

## 2. 墙钟原则：作者当时墙上的钟

git 的 author date（`2026-03-10T02:47:00+08:00`）自带作者提交时刻的**本地时区偏移**，钟点字段就是他当时墙上的钟。工具直接读取，**零时区换算**：分布式团队里，北京凌晨 2:47 和伦敦前一日 18:47 是两个真实的人生时刻，各自入桶。任何「统一换算成 UTC 再分桶」的做法都会把洛杉矶的傍晚误判成北京的深夜——本工具最核心的一条正确性测试就是：同一瞬间用两个时区表达，必须落进两个桶。

## 3. RR：有分母的怀疑

绝对数会说谎：凌晨缺陷多，可能只是凌晨写得也多。所以每个窗口报告两个份额：

```
D% = 该时段出生的嫌疑行 / 全部嫌疑行      （它贡献了多少返工）
W% = 该时段变更行数   / 全部变更行数      （它实际写了多少）
RR = D% / W%                            （单位产出的缺陷率）
```

RR=2 的读法：**同样写一行代码，在这个时段写下的那行，日后被修的概率是仓库平均水平的 2 倍**。判定 `DANGER` 需要 RR ≥ 1.5 且该窗口嫌疑行 ≥ 5——两个条件缺一不可，前者保证效应量，后者保证样本量。1.5 不是魔法数字，是「效应显著到值得一次对话」的经验起点（fork 后一行常量可改）。

产出基线用**变更行数**（adds+dels，numstat）而非 commit 数：凌晨「一行小修」和白天「三百行特性」都是一次 commit，按 commit 数计基线会把深夜的密度稀释 300 倍。

## 4. 嫌疑行启发式：诚实的不完美

**fix 识别**靠提交消息正则（默认 `fix|bug|revert|hotfix|patch|修复|修正`，大小写不敏感）。假阴性（「adjust billing logic」实为修 bug）会漏计；假阳性（「fix typo in README」）会把无害行计入。两个误差都在** diluted 而非偏向**——除非你的团队有系统性的消息习惯偏差（比如深夜修 bug 从不写 fix），RR 的方向仍可信。`--fix-pattern` 完全可替换；有缺陷跟踪系统的团队可以自己生成 sha 列表喂进来（PR welcome）。

**删除行 = 嫌疑行**的假设：修复的本质通常是替换写坏的行。它会把缩进调整、重构搬移也算成「嫌疑」——噪声是双向的、跨时段均匀的，对 RR 的分子分母同时起作用，方向上互相抵消。纯新增的行（`+` 行）不参与归因：一行从未存在过的行没有出生证明可言。

## 5. 统计纪律

- **整仓 < 20 嫌疑行 → insufficient**：报告开头自认「这是轶事不是统计」。宁可没有故事，不可硬造故事。
- **单窗口 < 5 行 → low-n**：有数字，但样本不配拥有结论。样例仓库里 03-06 窗口 RR=1.60 依然只给 low-n，这是特性。
- **相关 ≠ 因果**：RR 高的时段混杂着一切——深夜接的多是难任务（辛普森悖论的经典来源）、深夜人少 review 稀释、或者单纯那个时段写的代码域更脆。RR 回答的是「**哪里值得追问**」，不是「谁的错」。它的正确用途是开启对话：「这三个月凌晨的 RR 是 3，我们聊聊排班吧」——错误用途是绩效评估。
- **中位数偏差**：嫌疑行按「行」计而非按「缺陷」计，一个大 bug 改 30 行会压过 15 个小 bug。行是 git 的原生原子，缺陷不是——接受这个失真，胜过引入主观的「缺陷个数」口径。

## 6. 边界情形的处置

| 情形 | 处置 | 理由 |
|---|---|---|
| merge commit | 全局不可见（`--no-merges`） | 它的时间戳复述别人的工作，churn 也是搬运 |
| fix 追溯到 merge 的冲突解决行 | 记 **unborn**，不归因 | 冲突解决行没有出生证明，硬归因等于让 merge 时刻替冲突背锅 |
| `git mv` 改名后的行 | blame 穿透 rename，归因到真正的出生 commit | 搬家不洗出生地 |
| fix 本身是 root commit | 跳过（无 parent 可 diff） | 没有昨天，就没有嫌疑 |
| binary 文件的变更 | numstat 显示 `-`，churn 忽略 | 二进制没有行 |
| `--max-fix-commits 300` | 保留最新的 300 个 fix | blame 是逐文件考古，大仓库需要预算；截断方向恒定（丢最老） |

## 7. 伦理条款

时间戳是观察数据，不是自报数据——这既是它的力量（不表演），也是它的危险（无处可藏）。因此：纯本地运行、零上传；`--author` 服务的场景是「我看我自己的生物钟」，不是「查你」；报告里所有的判定词（DANGER/low-n/insufficient）都在说「数据的可信度」，从不在说「人的表现」。一个健康的用法闭环：个人先看自己的，愿意分享再进团队复盘；团队报告默认聚合，点名需要 opt-in。**本工具不接绩效系统**——接了的那一刻，所有时间戳都会开始表演（深夜 commit 改到白天的成本是零）。

## 8. FAQ

**Q: 为什么 3 小时一桶？**
24 = 3 × 8，八行表格正好一屏；逐小时桶噪声太大（单小时样本几乎必然 low-n）。`--bucket-hours 1/2/4/6/12` 都可调。

**Q: 我周末写代码但状态很好，会被冤枉吗？**
RR 只按小时段分桶，不看星期。周末的影响只在 `rhythm` 的 weekday 表里作展示，不参与判定。

**Q: fix commit 自己也改了行，会污染基线吗？**
会——fix 的 churn 也计入 W%。这是有意的：返工本身也是工作量，剔除它反而美化了真实成本。

**Q: rebase / squash 会毁掉出生时刻吗？**
会。rebase 把 author date 保留但 committer date 重写，squash 把多个出生合并成一个。本工具只读 author date（真实写入时刻的最好代理），但重写历史无法恢复——这是为什么应该在「还来得及」的时候跑。

**Q: 与本仓库其他点子的关系？**
同一片 git 矿脉的不同切面：gitweek 考古「做了什么」，bus-factor 丈量「谁懂什么」，todo-rot 记账「承诺了什么」，doc-drift 盯着「文档说的和代码做的是否一致」，witching-hour 追问「什么时候写的最容易坏」——时间维度的质量归因，此前是空白。若你只想知道「团队是否在熬夜」（负荷观测，而非缺陷归因），那是一个不同的产品问题，本工具刻意不做。

**Q: 下一步最有价值的一格拼图？**
把 fix commit 与 issue tracker 关联（消息里的 `#1234` 已经是现成的锚点），把「嫌疑行」升级成「确认缺陷行」，RR 的分子从启发式变成实证。数据结构已就绪（`defect_by_hour`），缺的只是关联层。
