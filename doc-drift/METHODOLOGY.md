# 方法论 · The Doc Drift Methodology

<!-- verified: 2026-08-16; ttl: 180d -->
`doc-drift` 不只是一个脚本，它是一种**对待文档的纪律**：文档不是写完就结束的装饰品，而是和代码一起部署、一起演进、需要一起验收的**活的产品**。本文讲清这套纪律背后的为什么，以及怎么把它落进日常工作。

---

## 1. 为什么文档需要「编译器」

软件工程解决「代码会坏」的办法，从来不是「更小心地写代码」，而是**装守门人**：

| 守门人 | 拦截什么 | 信号 |
|---|---|---|
| 编译器 / 类型检查 | 引用不存在的符号 | ❌ 编译错误 |
| 单元测试 | 行为回归 | ❌ 红灯 |
| Lint | 已知的坏模式 | ❌ 报警 |
| **文档守门人** | **文档与现实脱节** | **——空缺——** |

文档引用 `src/foo.py`，`foo.py` 改名了——没有任何信号。<!-- dd:ignore: 概念演示，非本仓库文件 -->文档说「先用 `init` 初始化」，命令改成了 `setup`——没有任何信号。<!-- dd:ignore: 概念演示 -->于是文档只能单方向腐烂，而腐烂的代价不是「文档错了」，而是**读者不再相信文档**：新人直接去问人（成本转嫁给老成员），老人说「看代码」（文档投入沉没）。

`doc-drift` 的主张：**给「文档与现实一致」一个机器判定的子集**，并让这个子集在 CI 里拥有和编译错误同级的否决权。剩下机器判不了的部分，用保鲜期制度显式地暴露出来，交给人工复审——而不是假装它们不存在。

## 2. 漂移三分类：哪些交给机器，哪些留给人

```
引用漂移（reference drift）
  文档提到的文件/目录/符号已不存在。
  → 机器全权判定：存在性检查，ERROR，CI 拦截。

保鲜漂移（freshness drift）
  声明当时是对的，但依赖环境/版本/前提，没人知道现在还对不对。
  → 机器管时间，人管真伪：verified 戳 + TTL，过期 WARN 催审。

语义漂移（semantic drift）
  文档字面仍正确，但意图已偏（比如架构文档描述的分层早已名存实亡）。
  → 纯人工。保鲜期制度的价值在于：它把「该复审的声明」定期推到你面前，
    让人工复审有一个确定的、可穷尽的对象清单，而不是「有空就把文档都看一遍」。
```

这个分类本身就是使用方法：**能自动化的绝不麻烦人，不能自动化的绝不装作自动化了。**

## 3. 保鲜期制度：给声明一个「保质期」

关键声明（构建方式、环境要求、版本适配、性能数字、任何「现在是」的断言）在段落或行上打戳：

```markdown
<!-- verified: 2026-08-16; ttl: 90d -->
本节构建方式适用于 macOS 13+ / Python 3.8+。
```

语义：

- `verified` 是**最近一次有人确认此声明为真**的日期，不是「文档写于」的日期。
- `ttl` 是这条声明的保质期（默认 180 天）。变化快的领域给短 TTL，稳定的给长 TTL。
- 过期 → WARN：**不是错误，是催审**。复审后真则更新日期，假则改文档——两个动作都让文档重新可信。
- 未来的日期 → ERROR：那是谎言，不是保鲜。

为什么 WARN 而不是 ERROR：如果把「没人复核」当错误，团队的反应会是**不再打戳**（戳成了负债）；只有当戳是廉价的可信资产时，制度才可持续。过期本身不证明文档错了，只证明「没人担保」——把担保状态可见化，正是制度的目的。

## 4. 引用规范：写文档的五条纪律

1. **指称文件就加反引号**：`examples/demo-repo/docs/guide.md`。反引号内（含代码块）的路径与裸文件名都会被验证——反引号即引用。
2. **指称符号用 `path::Symbol` 语法**：`examples/demo-repo/src/live.py::run_checks`。文件存在且符号在文件内，双重验证。
3. **类型提及要豁免**：写「每个点子都有 `README.md`」这种泛指时，行尾加 `<!-- dd:ignore: 类型提及 -->`。豁免必须带理由——半年后你还知道自己为什么豁免。
4. **示例值用占位符**：写 `<你的账本>.json` 而不是真实文件名，就不会被误判。
5. **每次改代码，顺手 `scan`**：它就是文档的 `make`。

## 5. 两个指标

- **漂移密度** = 问题数 / 检查引用数 × 100（issues per 100 refs）。跨项目可比，趋势比绝对值有意义。
- **保鲜率** = 未过期声明 / 已打戳声明。衡量的是「文档里有多少话仍有人担保」。

指标的目的不是考核写文档的人，而是让「文档健康」像测试覆盖率一样**可讨论**。

## 6. 融入工作流的三个位置

- **提交前**（开发者）：`doc-drift scan` 与 `make` 同级——改名文件的人当场看到他弄坏了哪篇文档，修复成本最低的时刻就是现在。
- **CI**（团队）：漂移红灯。引用漂移应该在 PR 里被拦截，而不是在事故后被发现。
- **文档复审日**（维护者，如每周 30 分钟）：只看 WARN 清单——它就是「哪些声明该重验」的确定答案。全部续期或改写后，`stamp` 生成新戳。

## 7. FAQ

**Q：为什么不做外链检查？** 那是 lychee 等工具的领域（需要网络、重试、缓存）。doc-drift 只管**仓库内部**的一致性——不需要网络，完全确定性，这正是 CI 想要的性质。

**Q：为什么不检查标题锚点（`file.md#section`）？**<!-- dd:ignore: 语法示例 --> 锚点解析需要完整 markdown AST 与各渲染器的 slug 规则（GitHub/VS Code/飞书各不相同），确定性差。留作未来可选检查。

**Q：裸文件名为什么不在正文里验证？** 正文自然语言里「详见 README」太随意，验证必误报。反引号内的文件名才是明确指称——这条规则把「引用」变成了一个**轻量协议**：你加反引号，工具就替你担保。

**Q：误报怎么办？** 三层出口：改措辞（用占位符）、`dd:ignore: 理由`（行级豁免，理由必填）、`--exclude`（整目录豁免，如示例 fixture）。每个豁免都留痕，都可被 grep 出来审计。

**Q：`--today` 为什么存在？** 让报告可复现（`--today 2026-08-16` 永远得到同一份报告），测试、归档、对比趋势都靠它。这不只是测试钩子——「以某日为基准的文档健康快照」本身就有用法。

**Q：和 [#1 决策债务](../decision-debt/README.md) 什么关系？** 互补的一对：decision-debt 记录「**我们为什么这么定**」（决策的债），doc-drift 守护「**文档说的还算数吗**」（文档的债）。一个管新信息的产生，一个管旧信息的失效。

## 8. 限制（诚实清单）

- 行级正则 + 围栏状态机，非完整 markdown AST；嵌套围栏、HTML 内联等边角不处理。
- 不验证文件「内容」是否仍匹配描述（语义漂移只能靠保鲜期 + 人工）。
- 符号检查是词级存在性（`\bSymbol\b`），不理解作用域/重命名。
- Windows 反斜杠路径不识别（本仓库约定正斜杠）。
