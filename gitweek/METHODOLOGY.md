# gitweek 方法论 · 让不可见工作被看见

> 工具只负责挖出事实；这份文档讲为什么要挖、挖出来之后怎么用。

---

## 1. 问题：你的周报在系统性说谎

不是故意的。是三重认知偏差让每个人写周报时都会漏掉大量真实工作：

1. **时长低估（duration neglect）**：回忆一段时期的工作时，人脑记住的是「峰值事件」和「结尾事件」，不是总量。周三下午那两小时痛苦的依赖升级，在周五的记忆里几乎没有痕迹。
2. **可见性偏差**：新功能有 demo、有截图、有人讨论；测试、文档、重构没有「亮相时刻」，它们的价值体现为*没发生的事故*——而没发生的事天然不可见。
3. **多仓库碎片化**：一天里你可能在 4 个仓库各留了 2 个小提交。单看主仓库，「这周没干啥」；事实上你的维护工作散落在各处。

后果不只是周报难写。**不被看见的工作不会被排期**——当团队里所有人都低估维护工作量，维护就变成「有空再做」，技术债的利率就开始复利（参见本仓库的另一个点子：[决策债务](../decision-debt/)）。

gitweek 的立场：先用确定性事实对抗记忆偏差，再谈表达。

## 2. 工作的可见性光谱

```
可见 ◄──────────────────────────────────────► 不可见
feat   fix   perf   refactor   test   docs   ci   build   chore   style
大块头，自己会记得写          碎、杂、不出彩，但让系统活着
```

这个光谱**不是价值判断**——fix 生产事故的可见工作和升依赖的不可见工作都重要。它标注的是**周报遗忘概率**。gitweek 的分类规则（前缀 → 关键词 → 路径）是确定性的、公开的、可调的（`gitweek.py` 顶部常量），你可以按团队习惯修改关键词表。

## 3. 周五仪式

```
① gitweek report --scan -p ~/dev          看全貌（2 分钟）
② 盯 Invisible work 一节，逐条问：「成果是什么？」（2 分钟）
③ --format md 生成草稿，改写 + 补下周计划（5 分钟）
④ 看 WIP：未提交的工作要么落盘，要么写进下周计划（1 分钟）
```

关键动作是第 ② 步的**改写**。git 消息是写给未来的自己的（「chore: bump flask」），周报是写给同事和老板的。规则：

| 改写前（活动语言） | 改写后（成果语言） |
|---|---|
| `chore: bump flask to 3.1` | 修复了 Flask 3.0 的已知内存泄漏，升级后 API 内存占用下降 ~15% |
| `test: cover discount edge cases` | 补齐折扣计算的边界用例，该模块测试覆盖率 41% → 78% |
| `refactor: extract tax calc` | 把税费计算拆成独立模块，为多地区税率铺路（下周接欧盟） |

活动语言回答「我做了什么动作」，成果语言回答「之后世界有什么不同」。**数字是最好的翻译器**——覆盖率、内存、延迟、错误数。gitweek 的 Overview（+/- 行数、触达文件、活跃天）就是给你提供这些数字的。

## 4. FAQ

**Q：我有好几个 git 身份（公司邮箱 / 个人邮箱），会漏吗？**
默认每个仓库用自己配置的身份（local 优先、global 兜底），所以「每个仓库里的我」都会被算上。跨仓库想收齐某个特定身份时用 `--author "name-or-email"`（正则）。

**Q：公司代码能跑吗？会联网吗？**
完全本地。gitweek 只调用 `git log` / `git status` / `git config`，不联网、不上传、不写任何远程。

**Q：rebase / squash 会影响统计吗？**
日期口径是 **commit date**（落地时间）而非 author date（编写时间），所以周五写的代码周一 squash 合入，会算在周一——这正是「仓库里发生了什么」的口径。改写历史会改变 commit hash，但本周内的正常 rebase 不影响统计。

**Q：为什么不算 code review、项目管理里的工作？**
诚实边界：本地 git 历史里没有这些数据。gitweek 宁可少报，不编造。review/issue 统计需要平台 API（GitHub/GitLab），如果你需要，可以基于 `--format json` 的输出自己接。

**Q：不可见占比很高，是坏事吗？**
不是。系统越成熟，维护占比越高。「这周 60% 是维护」本身是中性事实；它危险的唯一场景是**没人知道这个数字**——那才是失真的开始。

**Q：`other` 类别是什么？**
三层规则都没命中的提交（比如消息是 "wip" 且只改了业务代码）。它不参与不可见占比的分母，避免污染口径。

**Q：和决策债务（decision-debt）什么关系？**
同一系列的两次尝试：**让隐性认知成本可见**。决策债务管「悬而未决的决策」占用的注意力；gitweek 管「已完成却被遗忘的工作」。一个面向未来的选择，一个面向过去的产出。

## 5. 局限与诚实声明

- 分类是启发式的：没有 conventional 前缀的消息靠关键词和路径猜，会有误判（"dispatch" 含 "patch"）。所以规则完全公开、常量可调，且 `--format json` 输出原始数据供你自己复核。
- 行数是代理指标：+200 行可能是生成代码，-200 行可能是最难的精简。数字用于**唤起记忆和提供佐证**，不用于绩效排名。
- gitweek 不能替代记忆，只能校正记忆——最后把「活动」写成「成果」的仍然是你。
