# METHODOLOGY · 窗期的方法论

## 1. 滚动窗口为什么不能心算：它是一阶的，直觉是零阶的

人脑对「额度」的直觉模型是**月度话费**：这个月用了多少，月底清零重来。90/180 不是这种模型——它没有「这个月」，任意一天都是某个窗口的最后一天，占用是对过去 180 天的**滑动求和**。直觉的零阶模型（「我今年去了几次、大概几周」）与一阶滑动求和之间的误差，恰好在你最需要注意的那几周里最大：行程越密，误差越大。

更隐蔽的是**恢复直觉的错误**：人以为额度像体力，「休息几天就恢复了」。实际上释放是阶梯状的——某段旧行程完全滑出窗口的那一天，额度一次性回来 N 天（N = 那段的天数），之前每一天都只回 0 天。`balance` 的释放日程就是把这条阶梯画出来：你不是在慢慢回血，你是在等几次明确的到账。

## 2. 余额 ≠ 可住天数：本工具最重要的一条读数

`spare = 90 − used(today)` 是存量；「今天就走能连住几天」（walk）是流量——贪心地把你从今天开始每天都留在区内，直到某天的窗口峰值破 90。两者常常不相等，甚至方向相反：

- **walk > spare**：窗口尾部有旧行程正在滑出。样例账本 spare 7 天、walk 15 天——那 8 天的差额是 3 月行程在 09-11 到 09-18 之间逐日滑出还给你的。
- **walk < spare** 理论上不发生（今天出发至少能住 spare 天？不——若 spare 是靠未来将滑出的旧占用撑大的假象？不会，used 只含真实占用，spare 天内的每一天窗口占用 ≤ used(today) ≤ 90，恒有 walk ≥ spare）。所以本工具只报 walk ≥ spare，一旦你看到两者差距很大，那是回血在即的信号。

把这两个数印在同一行里，是这本账存在的核心理由：**看章的人只会算出 spare，看账的人才知道 walk。**

## 3. 已订的票也是占用的钱：窗口不赊账

账本允许记录未来的行程，并且让它们进入 used 的计算。这是刻意设计：机票已出、酒店已订的行程对窗口而言已经是扣款——被拒入境的从来不是「计划」，是拿着计划的你。`gate` 存在的意义就是在扣款发生之前报警：样例里那趟 10-02..10-15 的秋游贴线通过（89/90），但只差一天——任何想把行程改长一周的念头，`check` 会当场给出最晚离境日 10-30。

## 4. 重叠按并集计：一行数据语义，两种使用场景

同一区域的两段停留不可能在现实中重叠（一个人不能同时两次入境），所以账本内重叠是数据腐败，`validate` exit 2。但 `check` 构造的**假设行程**与已订行程重叠是另一个场景——改签延住。此时工具把重叠天按并集只计一次（rebooking semantics）：你把 14 天的秋游「延长」成 43 天，窗口看到的是一段 43 天的占用，而不是 14 + 43。

这个语义有一个漂亮的副作用：`when` 的假设行程也可以「吞并」计划中的短行程（把两段连成一次长住）。测试里那个「90 天永不可行」的反例构造因此必须让周期段短于行程长度（60 天周期）——170 天的周期会被一次 90 天的行程整体吞掉。注释里写明，防止未来的人（包括未来的自己）误以为是任意周期都行。

## 5. 无解就说无解：拒答比编造一个日期更诚实

`when` 的语义是「最早哪天出发能连住 N 天」。搜索上限 730 天，找不到就 exit 3——「730 天内没有这样的日子，考虑缩短行程或看释放日程」。它不会退而求其次给一个「最接近的」日期，因为**「最接近可行」的日期不存在**：可行与否在行程长度上是阶跃的，差一天就是 SAFE 与 OVER 的区别。样例里 11-29 出发第 30 天窗口 91 天超限，11-30 出发恰好 89 天合规——一次旅行之差，全在窗口尾部那两天旧行程的滑出时机上。这种临界只有逐日模拟算得出来，也正是人必须把账交给工具的原因。

## 6. 误用防范

- **别拿它当法律意见。** 工具按 180/90 的通用口径计算；个别国家的执行细则（补算规则、豁免、临时协定）不建模。落地前的重大决策请以官方计算器与边检口径为准——本工具是你的账本，不是你的律师。
- **别把账本当合规证据。** 它记录的是你声称的出入境事实；真正的凭证是护照章与出入境记录。账本的产出物是决策支持，不是申辩材料。
- **别只用 `balance` 不用 `gate`。** 余额是今天的快照，爆掉的是未来的某一天。样例里 83/90 看似安全，真正的压力测试是 10 月中旬的 89/90——不看 `gate` 的人永远不知道自己的窗口峰值在哪天。
- **别在未闭合行程上决策太久。** 离境留空的行程占用只计到今天，如果你实际已经出境却忘了闭合账本，余额会持续偏保守（少算额度）——偏保守是安全的，但会让 `when` 给出过晚的出发日。回家当晚闭合账本，只要十秒钟。

## 7. FAQ

**Q：为什么入境出境日都算一天？**
申根规则原文如此：停留天数含抵达日与离开日。这意味着「周五晚上到、周一一早走」是 4 天不是 2 天——大部分人对一次周末旅行的成本估算天生少算一半，账本从第一行就按真实口径记账。

**Q：其他国家的停留规则能用吗？**
窗口参数可调：`--window 365 --quota 180` 这类「半年内累计半年」的变体直接可算。但**口径不同的规则**（按自然年计算、按停留次数计算）不是本工具的模型，强行套参数会得到错误的安心感。账本的诚实条款在参数之前：模型不对，宁可不算。

**Q：为什么不做一个日历可视化？**
因为决策发生在终端里：订票网站开在浏览器，机票agent问「改到几号」，你需要的是一个能立刻回答 `check --entry --exit` 的命令，而不是一张要人眼扫描的图。日历看得见形状，exit code 看得见裁决——这本账选择后者。

**Q：多次入境但只算了大概日期怎么办？**
账本只求「章上有的事实」。日期记不准时用你 best knowledge 的日期，但知道两件事：占用误差最多差几天；`validate` 的重叠检查与 `history` 的峰值会帮你抓出明显记错的段落（一段与另一段咬合不上的行程会自己浮出来）。
