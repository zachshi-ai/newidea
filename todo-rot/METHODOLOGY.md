# METHODOLOGY · 承诺会计学

> todo-rot 的账本不是比喻，是一套有借必有贷的复式记账。本文记录每一条记账规则的动机、边界与已知局限。

## 1. 为什么「删除 = 还清」

一个承诺的存在形式就是那行注释。当代码 diff 把 `# TODO: x` 移除时，只有三种可能：

1. **事情做了**——还清；
2. **事情不做了**——作废（也是一种清偿：那张支票不再占用未来的注意力）；
3. **文本改了 / 搬家了**——旧票作废、新票生效。

工具对 1/2 不加区分（都退出流通，寿命封账），对 3 有显式识别（见 §4）。你如果坚持「只有事情真的做了才算还」，那是 code review 的职责范围，git 数据本身回答不了「为什么删」——工具只承诺把**什么时候开的、什么时候清的**算准。

## 2. 为什么用事件流而不是 `git blame`

常见的做法是 `git blame -L` 找每行 TODO 的最后修改时间，有三个致命伤：blame 给的是**最后一次改动**而非立据日；行号漂移后 blame 结果不可配对；删除的 TODO 在工作区根本不存在，blame 无从还原文票的寿命。事件流（`git log -p --unified=0` 重放）天然是**复式账**：加行=立据、减行=销账，已清偿支票的寿命是重放的副产品，`git mv` / 编辑 / 删除全部可判定。一次 log，全部事实。

## 3. 半衰期：中位数，而不是平均数

还清一张支票的用时是重尾分布：多数 TODO 要么一周内顺手清掉、要么拖成化石，平均数会被化石拉爆，中位数才是「这个团队说话算话的典型时长」。样本里哪怕只有 2 张已清偿支票，中位数也是合法且可复算的估计——置信区间宽，但方向不会骗人。

**僵尸判定：age > max(2 × half-life, 30 天)**。两倍半衰期在生存分析里的直觉：如果承诺的清偿是一个稳态过程，存活过 2× 中位数的个体属于长尾的尾巴；30 天下限防止「半衰期 2 天」的仓库把一切新票判成僵尸。没有已清偿样本时不做僵尸判定（输出「从未还过任何承诺」，这本身就是最重要的信号）。

## 4. 记账细则

| 情形 | 记账 | 理由 |
|---|---|---|
| 新文件 / 普通提交新增标记 | 立据 | — |
| 标记行消失（同文本无对应新增） | **还清**，寿命 = 销账日 − 立据日 | §1 |
| 同一提交内：旧文件减一行、新文件加一行、规范化文本相同 | **转址（re-site）**，立据日不变 | 搬家/重构不该洗白账龄；重命名检测没接住的 `mv` 也能靠它兜底 |
| `git mv` 改名（rename from/to） | 整个待偿队列随文件迁移，立据日不变 | 同上 |
| 整个文件被删除 | **自然死亡（died）**，不计入寿命池 | 债随人亡不是还钱，混进半衰期会系统性低估还钱速度 |
| 标记文本被编辑（配对失败） | 还清旧票 + 立新票 | 「改承诺」就是「取消旧承诺」；不这样做，半衰期会被文本微调无限刷新 |
| 同名承诺出现多份 | 逐张 FIFO 配对 | 清理时通常顺手先清最老的 |
| 配对键 | `marker + 规范化文本`（剥 owner/issue/日期、统一大小写标点、截 140 字符） | `TODO(alice): x` 与 `TODO: x` 是同一张票 |

已知边界情形：同一提交里在 A 文件还清、B 文件恰好新开一张**文本完全相同**的票，会被误判为转址（保龄）。发生率低，且误差方向是保守的（少算僵尸、多保账龄）。

## 5. 权重与锈蚀分

`rot = weight × age_years`，权重 TODO=1 / XXX=2 / HACK=3 / FIXME=4。这不是司法裁决，是**注意力优先级**：FIXME/HACK 是作者自己承认「代码现在是错的/歪的」，每多活一年都比「以后可以更好」的 TODO 更值得被看见。权重是模块级常量，fork 后改成你团队的风险口味即可；`audit --max-rot` 按总量设红线，不必纠结单张的绝对值。

## 6. 还票记在谁头上

**开票人**（立据时的作者），不是还票人。`halflife` 的 per-author 表回答的是「谁的承诺容易烂在账上」；「谁在帮团队还债」同样有趣但视角不同——从事件流里取销账提交的作者即可，留给需要的人实现（PR welcome）。

## 7. FAQ

**Q: `--as-of` 和直接跑有什么区别？**
`--as-of` 走纯历史重放：只重放 ≤ 该日的提交、账龄算到该日、不读工作区。用于可复现报告与测试。不带 `--as-of` 时以工作区扫描为准做对账：历史里有、工作区没有 → 「未提交的销账」（dropped）；工作区有、历史没有 → 「未提交的新票」（uncommitted）。

**Q: merge commit 会丢事件吗？**
`git log -p` 默认不展开 merge 的 diff。落在 merge 里的事件（罕见）不会被记账；如果分支工作流很重，可自行加 `-m` 相关逻辑，但注意 `-m` 会把整棵树重复计入两侧，需要去重——所以默认行为是「宁缺毋滥」。

**Q: 历史很短 / 刚 init 的仓库？**
没有已清偿样本 → 无半衰期、无僵尸判定，账本退化为带账龄的清单。工具会明说，不装懂。

**Q: 生成代码 / vendored 目录里的 TODO？**
`--exclude` 前缀排除，被排除路径的立据与销账都不入账（包括半衰期池）。

**Q: 它和 decision-debt（本仓库 #1）什么关系？**
decision-debt 管「**悬而未决的决定**」——没有写下来的东西；todo-rot 管「**写下来的承诺**」——写了但没人对账的东西。一个治失忆，一个治赖账。先用 todo-rot 找出僵尸承诺，再用 decision-debt 的方法论决定它到底是「今天就做」还是「正式放弃」。

**Q: 为什么只认大写标记？**
`TODO/FIXME/HACK/XXX` 是三十年沉淀下来的通用大写约定；小写 `todo` 在罗曼语族里是常用词（todo listo），误报代价大于收益。

## 8. 局限性清单（诚实版）

- 不理解语义：「TODO: 删掉这段」被删可能因为整段代码被删——按我们的定义这就是清偿，成立但宽松。
- 配对靠规范化文本，极端的重写会断链（还清 + 新票，误差方向保守）。
- 半衰期假设清偿过程稳态；团队风格突变（如引入 CI 门禁）后，历史半衰期会短暂失真——但工具的目的正是让这种突变可见。
- bot 立据（生成代码里的 TODO）计入开票人；介意就在 `--exclude` 掉的生成目录里。
