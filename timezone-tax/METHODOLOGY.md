# 方法论 · 时区税

本文回答「为什么这么算」和「这么算有什么用不了的地方」。先立三个立场，再进 FAQ。

## 三个立场

**1. 会议时间是一个分配问题，不是搜索问题。**
World Time Buddy、Google Calendar 的 colors、各种「最佳重叠时间」工具都把排会建模成搜索：在约束下找重叠最大的一格。但重叠最大只说明「大家都醒着」，不说明「代价被公平分摊」。只要候选格子里有人付的价比别人高，这就是一个分配问题——分配问题需要账本和轮换机制，搜索工具天然不提供。

**2. 没有账本的不公平是复利的。**
一场 23:00 的会可以靠善意消化；52 场就需要制度。而制度的前提是有人能拿出一张谁也反驳不了的表：「过去一年上海缴了 156 税点，柏林缴了 0」。工具的全部价值就在于这张表的存在——它把「凭什么总是我」从抱怨升级为事实。

**3. 诚实优先于讨好。**
如果轮换能改变缴税人，给轮换计划；如果不能，直说「结构性失衡，出路不在排会」。假装「再调调格子总能找到大家满意的」是排会工具惯用的安慰剂，本工具拒绝提供。

## FAQ

### Q1：为什么叫「税」？
因为三要素齐全：**隐性**（付税的人往往在会议邀请里才看到时刻）、**强制**（不来就掉队）、**累进于弱势者**（总部时区掌握排会权，税落在没有议价权的时区）。叫「成本」「代价」都太中性，掩盖了「谁承担」这个分配事实。

### Q2：税率 0 / 1 / 1.5 / 3 的依据？
- **深夜 3（22:00–06:59）**：压缩睡眠。睡眠科学里这不是「晚睡一小时」而是切掉睡眠结构，代价非线性。
- **清晨 1.5（07:00–08:59）**：没牺牲睡眠总量，但牺牲了晨间准备与家庭流程，且紧邻睡眠边界。
- **傍晚 1（18:00–21:59）**：侵扰个人时间，但人是醒着的、状态完整的。
- **黄金 0（09:00–17:59）**：工作时间本就是雇主的。

必须坦白：这是**声明式约定**，不是测量结论。它的价值不在精确，在于固定、成文、可辩论——团队完全可以改权重（配置里 `weights` 一个 JSON），但要像改宪法一样改：写进团队文档，全员知情。比「默认税率不完美」危险一百倍的是「每次排会临时争论什么叫晚」。

### Q3：为什么只按会议开始时刻计税，不管时长和跨带？
一个 15:30 开始、跨过 22:00 的 60 分钟会，确实应该拆带计税。v1 按**开始时刻**整场计税，是刻意的简化：会议密度分布里跨带是少数，而拆带会让账本失去「一眼能对账」的性质（税单必须是员工自己口算能验证的数）。方法论上我们选择可核验性优先于精确性。改进路径明确：把 `bill_at_utc` 换成按带拆分的积分即可，账本格式不用动。

### Q4：夏令时为什么用配置驱动而不是系统时区表？
三个原因：① 零依赖承诺——`zoneinfo` 是 Python 3.9 才进标准库，仓库约定 3.8+；② **确定性**——不同机器的系统 tzdata 版本不同，账本必须换谁跑都一样；③ 显式优于隐式——团队成员在哪个时区本来就该是团队文档的一部分，而不是操作系统的。代价是 DST 切换日按配置的 `MM-DD` 近似（美国实际是「三月第二个星期日」这类规则），与真实切换日最多差几天，且切换瞬间按日历日而非精确时刻——对周粒度的排会结论无影响，`YYYY-MM-DD` 绝对区间可供较真的团队逐年代填写。

### Q5：缴税基尼 0.3 / 0.5 的警戒线怎么来的？
借收入基尼的惯用分级（0.3 以下相对平等、0.4+ 差距偏大、0.5+ 高度集中）取宽松档，因为会议税负的样本量小（几个成员、几十场会），阈值太敏感会狼来了。它同样可配置（`--gini-warn/--gini-alarm`）。比阈值更重要的是两个端点信号：**基尼=1**（一人全缴）和**最惨比率=∞**（有人从未缴税）——这两个数字出现时不需要统计直觉，所有人都该看得懂。

### Q6：为什么「轮换无效」是最重要的输出？
因为它反直觉且只有计算能发现。税带是本地挂钟的**单调**阶梯，可行带往往只有一两小时宽，带内各格的缴税人集合常常完全相同——这时每换一格都是「同一批人换一种姿势缴税」。人力直觉会以为「轮换总能公平」，工具会告诉你哪些团队形状下这个直觉是错的（示例的四地团队就是），并指出真正的出路：**拆会**（按区域各开一场，记录纪要）、**降频**（隔周会+异步纪要）、**异步化**（录屏+书面更新）。轮换有效的情形（如示例的旧金山+班加罗尔二人组）同样值得知道——那说明你的组织分布还有救，把轮换写成制度即可。

### Q7：和「轮流承担深夜场」的老办法有什么区别？
区别在**仲裁权**。老办法靠自觉和人情，通常退化成「谁好说话谁多来」。本工具把选择规则写死成代码：每周选「选完之后累计税负的最大值最小」的格子，并列比总税、再并列取更早——同输入必同输出。规则确定性意味着没人需要在会议上为「为什么这周是我们在半夜」辩护，答案在算法里，且有账本可查。

### Q8：已知局限（v1 明确不做的）
- **频率单一**：假设每周一场同频会议；多场不同频会议应各自建账本。
- **公平≠平等**：有人自愿换深夜场（带娃白天接送等），工具按人头计税看不见个人偏好；账本是集体账，个人豁免应该在团队文档里另行约定。
- **半天假/节假日/出差**：只认工作日配置，不接个人日历——零依赖与隐私的代价。
- **迟到早退、会议实际取消**：`record` 记的是计划税单；真实世界的取消应该不记账（工具不假装知道你没开会）。
- **法定节假日跨国差异**：workdays 是全团队统一的周一到周五，不做国别日历。

### Q9：隐私？
两个输入文件都不含会议内容、讨论记录或任何个人信息 beyond 时区。账本里只有「某 UTC 时刻、每人几个税点」。纯本地计算，不联网。

### Q10：怎么在团队里落地？
第一步不是轮换，是**先记账**：把过去半年例会的 UTC 时刻批量 `record` 进账本，`report` 出来贴进下次排会讨论——大多数团队会在这一步就被自己的基尼吓到。第二步才是把 `plan` 的轮换（或「结构性失衡」诊断）写成排会制度，每季度审一次账本。工具只负责让数字存在；把数字变成制度的是你。
